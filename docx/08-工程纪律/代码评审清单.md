# 代码评审清单

## TL;DR

评审不是“看一遍 diff”，而是按正确性、分层、异步、性能、可测性、安全和文档七类问题逐项核对。单人维护也必须完成自审；发现阻塞项不得以“后续再改”合并，发现可确认技术债必须登记 TD 编号。

## 1. 评审分级

| 等级 | 含义 | 响应时限 |
|---|---|---|
| 阻塞 | 会导致错误、数据丢失、安全风险、门禁失败或破坏架构契约 | 合并前必须解决或正式豁免 |
| 建议 | 可维护性、性能、可读性问题，不立即阻断功能 | 24 小时内回复，决定本 PR 处理或入台账 |
| 可选 | 偏好、未来优化、非当前目标 | 记录即可，不阻塞 |

## 2. 正确性

- [ ] 正常路径、空数据、缺字段、错误响应是否都有行为？
- [ ] 是否改变了播放模式、音质降级、缓存优先级、登录态等既有语义？
- [ ] 是否存在竞态：每个 await 后是否验证请求代次/队列版本？
- [ ] 错误是否会被静默吞掉？grep：grep -R "catch (_) {}" lib/；当前约 22 处。
- [ ] 是否新增了重复请求、重复下载、重复监听器？
- [ ] 是否有回归用例或明确引用已有用例？

## 3. 分层与依赖

- [ ] services 是否反向依赖 ui/controllers？
- [ ] controllers 是否依赖 ui？
- [ ] models 是否保持纯数据，不引入业务层？
- [ ] UI 直接调用 MusicApi 是否为一次性展示；跨页面状态是否应进入控制器？
- [ ] 新服务是否由 main.dart 装配，是否绕过手动 DI 自行 new？
- [ ] 是否新增静态单例而未说明测试替换方案？

## 4. 状态与生命周期

- [ ] ChangeNotifier 状态改变后是否 notifyListeners？
- [ ] 高频 position 更新是否避免触发全局重建？
- [ ] StreamSubscription、Timer、AudioPlayer、MethodChannel listener 是否 dispose？
- [ ] AppLifecycleState paused/detached 时是否 flush 必要持久化？
- [ ] 页面是否在异步回调后检查 mounted？

## 5. 异步与错误

- [ ] Future 是否 await 或显式 unawaited？
- [ ] catch 是否区分可降级与必须上报的错误？
- [ ] API 重试是否只用于幂等请求？
- [ ] 是否泄露原始响应体、token、路径或用户隐私？
- [ ] 错误信息是否有用户可读文案，而非直接展示 exception.toString？

## 6. 性能与资源

- [ ] 页面 build 是否创建服务、读文件或发网络请求？
- [ ] 列表是否使用稳定 key、懒加载和图片尺寸约束？
- [ ] 是否引入全目录扫描、全量 JSON 重写或每帧磁盘 IO？
- [ ] 缓存是否有上限、低水位、失败缓存和并发合并？
- [ ] 新增依赖是否增加包体积、平台插件或构建时间？

## 7. 可测性与文档

- [ ] 纯函数是否抽出并有单测？
- [ ] 是否提供依赖注入点，避免直接实例化原生服务？
- [ ] API、模型、设置键、缓存目录变化是否同步更新 04/05 文档？
- [ ] 技术债是否登记 TD；任务是否关联 T-Mx-nn？
- [ ] 是否运行 node docx/tools/check-docs.js？

## 8. 安全与平台

- [ ] 是否提交密钥、token、keystore、APK 或 local.properties？
- [ ] Android 权限是否最小化，新增权限是否有拒绝降级？
- [ ] 是否考虑 Android/iOS/桌面/Web 平台差异？
- [ ] MethodChannel 方法名、参数、返回值是否同步原生文档？
- [ ] release 构建是否使用正确签名和 versionCode？

## 9. 单人自审流程

1. 先读关联知识库文档和技术债条目。
2. 用 git diff --check 检查空白与冲突标记。
3. 按本文清单逐项勾选，阻塞项写在 PR/提交正文。
4. 运行 format、analyze、test、文档健康检查。
5. 24 小时后再次看 diff，重点检查异步竞态和边界。
6. 合并后更新台账与版本文档。

## 10. 约束与坑

- 清单不能替代真实设备验证，尤其后台播放、通知、悬浮窗和文件权限。
- 代码行数以 LF 口径为准；引用非空行必须标明口径。
- “测试通过”只说明现有测试通过，不代表未覆盖路径正确。
- 评审发现的风险不能只留在评论区，必须进入 TD 台账或明确接受。
