# 开发纪律总则

## TL;DR

1. 本项目当前是**单人维护、master 单主干、无 CI**，纪律的执行力完全依赖「脚本化 + 自检清单 + 台账留痕」。
2. 全部纪律分四阶段：**开工前 / 开发中 / 提交前 / 合并后**，编号 E-01 ~ E-23，每条都有可核对的执行方式与违反后果。
3. 「禁止在 master 上直接开发」在单人维护期属于**受控例外**（见 §3），一旦出现第二名贡献者或接入 CI，例外立即失效。

## 2. 四阶段总则

### 2.1 开工前（E-01 ~ E-05）

| 编号 | 纪律 | 执行方式 | 违反后果 |
|---|---|---|---|
| E-01 | **先读文档再改代码**。动手前必须读完该改动对应的知识库文档，未读到对应文档时先补文档 | 按 `docx/README.md:43-54`「快速入口」表定位文档；读完后在提交正文写明「参考文档」 | 返工：改动与既有约定冲突，需重做 |
| E-02 | **确认改动落在哪一层**。明确本次改动属于 config / core / models / services / controllers / ui 中的哪一层，禁止跨层顺手改 | 改动前列出将修改的文件清单，对照 `docx/02-架构设计/分层架构与依赖规则.md:74-78` 的越层例外表 | 架构腐化；评审阻塞 |
| E-03 | **先查技术债台账**。确认本次改动是否命中已登记条目（TD-xx），命中则在同一提交内更新台账状态 | `grep` `docx/06-质量保障/已知问题与技术债台账.md` 检索关键词 | 台账失真，重复登记 |
| E-04 | **破坏性改动先写技术方案**（见 E-11）。改动涉及存储键、公开方法签名、API 契约、数据目录时，先产出方案再写代码 | 方案写入 `docx/09-模板/技术方案模板.md` 对应结构，存于 `07-推进计划/` 或 PR 描述 | 影响面失控；可能数据损坏 |
| E-05 | **工作区必须干净再开工**。开工前 `git status --short` 只允许出现已知的未跟踪文件 | `git status --short` 输出为空或仅有 `docx/` 等预期项 | 误提交无关文件；diff 不可读 |

### 2.2 开发中（E-06 ~ E-12）

| 编号 | 纪律 | 执行方式 | 违反后果 |
|---|---|---|---|
| E-06 | **禁止在 `master` 上直接开发**。任何改动必须落在独立分支；单人维护期的例外见 §3 | `git rev-parse --abbrev-ref HEAD` 必须不是 `master`（例外期改为：提交前记录分支名） | 见 §3 例外失效后：主干不可回退 |
| E-07 | **单次改动单一目的**。一个提交/一个分支只解决一件事，禁止「顺手修一下」 | 提交前自问：能否用一句话说完本次改动的目的？不能则拆分 | 评审失效；回滚困难 |
| E-08 | **小步提交**。改动尽量控制在可独立验证的粒度，历史实测均值约 4.3 个文件/提交 | `git show --stat` 检查文件数与行数；单提交建议 ≤ 10 个文件 | 冲突面扩大；bisect 失效 |
| E-09 | **不夹带无关重构**。重构与功能/修复必须分提交；纯格式改动单独提交（`style:`） | 提交前 `git diff --stat` 逐文件确认动机一致 | 阻塞修复被拖延；评审成本翻倍 |
| E-10 | **改契约同步改文档**。触及 API 端点、数据模型字段、设置键、缓存策略时，同一提交内更新对应 L1 契约文档 | 对照 `docx/00-元数据/文档规范与维护约定.md:91-100` 触发式更新表 | 文档静默腐烂；下次回归误判 |
| E-11 | **破坏性改动先写技术方案**。凡涉及存储键改名、公开方法签名变更、目录迁移、协议变更，先出方案并给出迁移与回滚路径 | 方案须包含：动机 / 影响面 / 迁移步骤 / 回滚步骤 / 验收方式 五项 | 用户数据丢失风险；返工 |
| E-12 | **不得吞异常**。新增 `catch` 必须限定异常类型（`on Exception` / `on PlatformException`）并至少记录日志；禁止 `catch (_) {}` | `grep` 检索 `catch (_)`；当前全库 63 处，属待收敛状态 | 静默失败，线上问题不可见（TD-25） |

### 2.3 提交前（E-13 ~ E-18）

| 编号 | 纪律 | 执行方式 | 违反后果 |
|---|---|---|---|
| E-13 | **格式化**：提交前必须执行 `dart format` | `dart format lib test`，并用 `dart format --output=none --set-exit-if-changed lib test` 校验 | 风格漂移；后续 diff 噪声 |
| E-14 | **静态分析**：`flutter analyze` 不得新增违规 | `flutter analyze --no-fatal-infos`（当前基线 11 条 info，见 §6） | 门禁长期红，等于没有门禁 |
| E-15 | **测试**：受影响模块的测试必须通过 | `flutter test`，判定以 stdout 的 `All tests passed!` 为准 | 回归缺陷流入主干 |
| E-16 | **自审 diff**：提交前逐行读一遍 `git diff --staged` | 重点看：调试打印、注释掉的代码、临时文件、凭证 | 调试代码入库 |
| E-17 | **提交信息合规**：按 `type(scope): subject` 格式，冒号用半角 | 对照 `docx/08-工程纪律/Git与提交纪律.md` §3 的 type/scope 表 | 历史不可检索 |
| E-18 | **禁止提交的内容**：`build/`、`.dart_tool/`、`local.properties`、签名文件、`.env` | `git status --short` + `git check-ignore -v <path>` | 凭证泄露；仓库膨胀 |

| 编号 | 纪律 | 执行方式 | 违反后果 |
|---|---|---|---|

## 3. 「禁止在 master 上直接开发」的例外与补偿（单人维护期）

### 3.1 例外成立的条件（必须全部满足）

| # | 条件 | 判定 |
|---|---|---|
| 1 | 仓库只有一名有写权限的维护者 | `git log --format='%an'` 与 GitHub 协作者列表 |
| 2 | 无 CI、无强制 PR 检查 | 仓库无 `.github/`（实测成立） |
| 3 | 改动不涉及 E-11 定义的破坏性变更 | 自评 + 台账登记 |
| 4 | 每次提交均可独立回滚（无跨提交依赖） | `git revert` 可单独生效 |

### 3.2 补偿措施（例外期必须执行）

| # | 补偿措施 | 执行方式 | 为什么能补偿 |
|---|---|---|---|
| C-01 | 提交前跑完整本地门禁 | `scripts/check.ps1`（计划中，T-M0-05）；未落地前手工执行 §2.3 命令 | 替代 CI 的自动阻断 |
| C-02 | 每次提交必须能在干净工作区回滚 | 提交后 `git stash` 不适用时用 `git revert --no-commit` 试跑 | 替代分支的隔离性 |
| C-03 | 保留推送前的本地分支快照 | 推送前 `git branch backup/<日期>` | 提供回退点 |
| C-04 | 提交信息必须写清「为什么」，而非「做了什么」 | 提交正文必填动机段 | 替代 PR 描述的上下文 |
| C-05 | 破坏性改动一律走分支（不适用例外） | 见 E-11 | 高风险改动必须隔离 |

### 3.3 例外退出条件

出现下列任一情况，例外**立即失效**，必须改为「分支 + PR + 评审」流程：

| # | 退出触发 | 依据 |
|---|---|---|
| 1 | 出现第二名有写权限的贡献者 | `docx/00-元数据/文档规范与维护约定.md:109` 责任划分需重新登记 |
| 2 | 接入 CI（T-M1-01） | 门禁可自动阻断，无需靠自律 |
| 3 | 引入发布分支/热修复分支（见 KA-08-04） | 主干需保持随时可发布 |
| 4 | 单次改动涉及 E-11 破坏性变更 | 例外条件 3 不满足 |

## 4. 违反后果分级

| 级别 | 定义 | 处置 | 记录位置 |
|---|---|---|---|
| L1 提醒 | 不影响正确性，仅风格/信息缺失 | 当场修正，无需登记 | 无 |
| L2 返工 | 需要重做提交、拆分提交或补文档 | 重做后重新走 §2.3 门禁 | `docx/06-质量保障/已知问题与技术债台账.md`（若暴露债务） |
| L3 回滚 | 已进主干的缺陷/破坏性改动 | `git revert` + 缺陷登记（KA-BUG-YYYYMMDD-nn） | `docx/08-工程纪律/缺陷处理纪律.md` 流程 |

> 判定原则：**能通过脚本自动发现的，一律归 L2 以上**（因为脚本已在门禁里，属于明知故犯）。

## 6. 约束与坑

| # | 约束/坑 | 事实 | 影响 |
|---|---|---|---|
| 1 | 无 CI 时门禁全靠自律 | 仓库无 `.github/`、无 `scripts/` | 纪律无法被强制（TD-04） |
| 2 | `flutter analyze` 默认退出码为 1 | 11 条 info，`--fatal-infos` 默认 on | 直接当门禁会长期红（T-M1-02） |
| 3 | PowerShell 调用 `flutter test` 退出码不可信 | stderr 的「assets will be downloaded」被记为 NativeCommandError | 误判测试失败（见 `docx/06-质量保障/测试策略与现有用例.md:52-54`） |
| 4 | 单人维护的自评审有效性有限 | 无第二双眼睛 | 必须靠清单 + 隔夜复查补偿 |
| 5 | 纪律文档本身会过期 | `docx/` 已出现索引与实测不一致（README 称 9 个测试文件，实测 7 个） | 需按 D-09 标记待重写并登记 |
