# 文档与知识管理纪律

## TL;DR

文档是代码的工程资产，不是提交说明的附属品。04-数据与接口和 05-平台与原生属于契约级文档，必须与代码同提交；新增文档必须先分配唯一编号、登记 README、通过 docx/tools/check-docs.js。文档与代码不一致时必须显式标待重写，禁止静默腐烂。

## 1. 变更触发对照表

| 代码变更 | 必须同步文档 |
|---|---|
| 新增/删除 API 端点 | 04/API-端点清单、API-契约总览、MusicApi |
| 修改 API 参数/响应 | 04/数据模型参考、API-Schema索引、API-契约总览 |
| 新增/修改设置键 | 04/本地存储与配置项清单、UI 页面清单、对应控制器 |
| 修改缓存目录/TTL/上限 | 03/服务层-缓存体系、04/本地存储与配置项清单、TD 台账 |
| 修改播放状态/队列 | 03/PlayerController、音频与后台播放、测试策略 |
| 新增 MethodChannel/权限 | 05 三篇文档、模块文档、发布检查清单 |
| 修复缺陷 | 技术债台账、回归用例库、对应模块文档 |
| 新增技术债 | 台账、WBS、风险登记册（若有外部风险） |
| 发布版本 | update.md、版本历史、路线图、发布模板记录 |

## 2. 新增文档流程

1. 判断所属目录与级别。
2. 在 README 的文档编号总表分配唯一编号。
3. 创建文件头元信息块。
4. 写 TL;DR、现状、设计说明、约束与坑、待办与关联。
5. 关键结论写文件:行或文件:方法锚点。
6. 在 README 全量索引登记。
7. 运行 node docx/tools/check-docs.js。
8. 与代码同一提交，不得先改代码后长期补文档。

## 3. 契约文档纪律

- 04 与 05 的文档级别为 L1，字段、端点、权限、平台能力变化必须同提交更新。
- API-端点清单和 API-Schema索引为自动生成物，只能运行 node docx/tools/gen-api-docs.js 更新。
- 自动生成物变更必须检查 api.json diff，不得手工制造假接口。
- 文档写愿景时必须放到 07；01~06 只描述当前事实。

## 4. 过期与冲突处理

| 情况 | 处理 |
|---|---|
| 发现一处不一致 | 立即登记 TD，文档头状态改为待重写或在约束与坑注明 |
| 暂时无法确认 | 写“待核实”、记录证据和验证命令，不得猜测 |
| 两篇文档冲突 | 以 L1 契约文档和代码为准，保留冲突说明并统一修订 |
| 文档失去用途 | 标记已废弃并保留迁移链接，不直接删除 |
| 编号冲突 | 以 README 编号总表为准，重新归一后全库检查 |

## 5. 术语与决策

- 术语唯一来源是 00-元数据/术语表.md。
- 重大决策记录背景、选项、取舍、结论、日期和影响面。
- 会议结论不得只存在聊天记录；必须落到对应文档或决策记录。
- “缓存”“播放缓存”“缩略图缓存”“下载”不得混用。

## 6. 健康检查与季度核查

每次文档变更执行：node docx/tools/check-docs.js。每季度执行一次人工核查：

- 抽样 10 个文件:行锚点与源码对照。
- 对照 pubspec、api.json、Manifest、设置键注册表。
- 检查 README 链接、编号、文档健康度。
- 复查 TD 条目是否仍存在、是否已关闭。
- 检查生成文档是否由当前 api.json 产生。

## 7. 约束与坑

- checker 只能发现结构问题，不能判断内容真假。
- 外链有效性不能由本地脚本保证。
- 自动生成文件的行数和表格会随 api.json 变化，不能依赖固定行号。
- 文档过度复制源码会造成双份维护，应优先写方法名和锚点。
