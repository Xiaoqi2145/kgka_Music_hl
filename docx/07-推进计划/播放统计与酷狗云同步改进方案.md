# 播放统计与酷狗云同步改进方案

> 文档编号：KA-07-08
> 级别：L3 📋
> 状态：草案
> 关联代码：`lib/controllers/player_controller.dart`、`lib/services/playback_stats_service.dart`、`lib/services/music_api.dart`、`lib/ui/pages/playback_stats_page.dart`
> 最近更新：2026-11-21
> 变更触发条件：统计口径、云端接口契约、平台播放信号或功耗预算变化时复核

## TL;DR

KAmusic 先独立记录本机实听时长和播放次数，再按需读取酷狗账号的累计时长和排行。云端回写采用低频批次，按接口验证结果分阶段开放。统计复用已有播放事件，锁屏时只累计和合并保存本机数据。

## 1. 两个项目的现状

| 能力 | EchoMusic 的实现 | KAmusic 的实现 |
|---|---|---|
| 本机统计 | `src/renderer/views/History.vue:218` 从本机历史计算播放次数，时长按曲长乘播放次数估算。`src/renderer/stores/historyStore.ts:160` 记录本机历史。 | `lib/controllers/player_controller.dart:1181` 在播放提交时分别记历史和次数，恢复提交也走该调用点。`lib/services/playback_stats_service.dart:129` 按歌名和歌手名聚合，同名歌曲会合并。 |
| 实听和云端时长 | `src/shared/listeningSession.ts:38` 用单调时间和位置推进估算实听。`src/renderer/stores/player/listeningTime.ts:20` 将播放起止事件与等级累计拆开，等级侧每满 60 秒查询基线后写增量。`src/renderer/stores/user.ts:399` 可读取等级累计 `d_sec`。 | `lib/controllers/player_controller.dart:3778` 在 `isPlaying` 且有歌曲时用墙钟累计，每分钟检查一次。每累计 30 分钟调用 `/listen/timeadd`，成功后本机时长才加 30 分钟。短时、断网和关闭上报时会漏记本机时长，当前判据也可能将缓冲算入。 |
| 云端历史与排行 | `src/renderer/stores/player/history.ts:16` 按播放进度门槛调用 `/playhistory/upload`，对当前曲目去重。`src/renderer/api/user.ts:388` 提供 `/user/history` 封装，`History.vue` 实际读取本机历史。 | `api.json:3967` 列出上传历史，`api.json:5276` 和 `api.json:5289` 分别列出最近历史和听歌排行。当前统计页从本机服务取数。这份 API 描述未列出 `/user/grade/info` 或 `/user/listen/report`。 |
| 持久化 | 本机历史通过 Electron 存储接口读写。 | `lib/services/playback_stats_service.dart:129` 每次记一首复制两张计数表，`lib/services/playback_stats_service.dart:178` 在 5 秒防抖后编码并覆写完整 JSON。历史服务另有一个 5 秒写入防抖。 |

EchoMusic 引用以本地工作区 `c1c48f9a` 和 `server` 子仓库 `62730f9` 为准。其接口与行为用于对照设计，KAmusic 上配置的服务端能力需单独核实。

## 2. 方案取舍

| 方案 | 收益 | 成本与适用范围 |
|---|---|---|
| 按 EchoMusic 的节奏移植 | 账号时长更新快，可上报逐曲起止事件 | 等级每小时最多约 60 次读和 60 次写，逐曲事件另外计。桌面参考实现的请求节奏会占用移动端功耗预算。 |
| 本机实听、按需读云、受限回写 **（采用）** | 本机即时可用，账号统计可跨端查看，写入有固定预算 | 云端更新有延迟，需要确认接口、重试和并发语义。 |
| 本机实听和只读云端统计 | 客户端改动及网络成本最低 | 适合作为首个云端版本，能展示酷狗数据。KAmusic 播放对酷狗历史和等级的同步还需后续写入能力。 |

## 3. 统计口径与本机数据流

| 指标 | 定义 |
|---|---|
| 本机播放次数 | 一次独立播放出现首段可信的实际推进后记一次。暂停恢复、seek、故障重载和同一曲的重复回调沿用原播放会话；真实重播、单曲循环重新开始和无缝进入下一首建立新会话。 |
| 本机实听时长 | 累计有效播放的真实经过时间，覆盖可播放的本地文件、离线下载和云盘。例：2 倍速连续听 30 秒，本机实听加 30 秒。 |
| 本机榜单 | 按稳定的曲目和艺人标识聚合，标题和艺人名称用于展示。有明确曲库 `mixsongid` 的曲目优先用该标识，其余来源用带命名空间的稳定键。沿用每次播放归属一组艺人的口径，保留现有 Top 10、累计次数和首次播放时间。 |
| 酷狗账号统计 | `d_sec`、等级、排行各按服务端确认的字段展示，标注查询时间。账号时长可能包含这台设备已经同步的播放，两套数值各自显示。 |

在 `PlayerController` 的提交、原生过界和状态回调中维护播放会话，复用现有位置与播放器状态事件。计时仅在已确认的音源、`playing && ready` 且位置可信推进时累加。seek、暂停、缓冲、中断、倍速变化、音源切换都切断采样基线。用 `min(单调时间差, 有效位置差 / 倍速)` 限制可计入时长。位置采样过期或跨越不连续点时跳过该段。播放实例标识与加载序号独立，避免错误重载和无缝过界被重复计数。

高频路径只更新少量内存字段，按需从现有进度事件采样，初始建议约 1 秒一次。上线前确认各平台输入是实际进展信号，或由可核实的新鲜锚点和状态共同支持。单纯外推的进度条位置不能证明出声。锁屏下有可靠事件时继续统计；系统挂起导致信号中断时保守跳过，不为补齐数据唤醒应用。用实际锁屏数据校准各平台采样间隔和长间隔判据。

只在计数或时长有变化时标记待保存。每累计约 5 分钟有效播放，沿已有事件路径提交一次持久化。本机统计与最近播放历史共用检查点，合并相邻生命周期回调和并发提交。进入后台、显式停止、正常退出和切账号时只提交脏数据，普通切歌、暂停、seek 只更新内存。播放会话的恢复快照继续沿用现有保存策略。读页面先取内存快照，按变更版本计算并缓存 Top 10。首版保留 `SharedPreferences`，播放期间原地更新内存聚合，按检查点生成快照。若大历史量下全量序列化或写入超过预算，在相应平台切换到增量存储后再开放该版本。

## 4. 酷狗接口与同步策略

| 接口 | 建议用法 | 开放条件 |
|---|---|---|
| `/user/grade/info` 查询 | 统计页展示累计听歌秒数和等级。 | 用 KAmusic 的登录会话验证接口可用、`d_sec` 单位和返回结构，并覆盖默认及自定义服务端的能力差异。 |
| `/user/listen` 或 `/user/history` 查询 | 先核实前者的排行语义；后者只提供已确认含义的最近历史。首屏选择符合用途的一个接口。 | 确认时间范围、排序、计数字段和游标。缺少全量时展示服务端返回范围。 |
| `/playhistory/upload` 写入 | 只对已开启同步、具有可靠 `mixsongid` 的曲库播放入队。门槛沿用 EchoMusic 的 `min(曲长, max(15 秒, 50% 曲长))`，以累计有效媒体播放量替代当前位置。未知曲长按 15 秒，单次播放只入队一次。 | KAmusic 契约列为 POST，EchoMusic 前端用 GET，且其参考代理模块每次只发一条。确认当前部署的 HTTP 方法、业务回执、真实批处理及 `pc` 的含义后开放。 |
| `/user/grade/info` 写入 | 若确认支持，用更低频的批次替代 `/listen/timeadd`。提交只使用开启同步后，同一账号下已核实且尚未发送的有效时间。 | 验证允许的增量和频率、重复提交、多设备同时写入及延迟结算。EchoMusic 的内存基线只适用于单客户端观察，不能解决跨设备同时读取旧基线再写入的冲突。 |
| `/user/listen/report` | 保留为起止事件的调研项。 | 仅当读写联调证明相应指标确实依赖起止事件，且实测能满足网络预算时再评估。 |

### 读写触发

- **读取。** 统计页进来先显示缓存，超过 15 分钟后刷新，支持用户主动刷新。同账号同接口并发请求合并，自动读取单次尝试。同一轮最多查时长和一个榜单或历史接口。分页或详细历史由页面操作发起。网络失败时保留上次成功结果和更新时间；接口缺失时该项不可用。
- **写入。** 新的云历史同步默认关闭。前台有播放或已有网络活动时检查到期批次，最多每 30 分钟一次同步窗口，按账号只允许一个在途批次。初始预算为每 30 分钟最多 1 次历史写入（最多 20 条，要求真正批处理）、1 次等级基线读取和 1 次等级写入，失败尝试和重试同样计入。代理逐条转发需按实际请求数验收，超过预算就保持只读。后台、锁屏、离线仅积累本地，回前台且条件满足时再提交。上报默认避开蜂窝网络，可随用户设置调整。复用应用已经知道的网络状态，网络切换不主动唤醒。历史队列初始限 100 条、保留 24 小时，淘汰最旧条目。等级时长按实测契约限制每个窗口的增量及积压期限，避免离线恢复后突发追报。本机累计值不受队列淘汰影响。
- **失败处理。** 对有明确未入账证据的可重试失败，只在下一次符合条件的前台同步机会处理，设置 30、60、120 分钟退避并封顶。超时、断连、进程被杀等导致入账结果不明时，用稳定的批次 ID 查回执或幂等重试。接口无此能力时保留未知状态，跳过增量重放。写接口禁用 HTTP 通用自动重试。判成功同时核验 HTTP、业务状态和必要字段，因此需保留通用 `unwrapData` 可能丢失的响应外层字段。发送前在持久化队列标记在途，进程恢复时按未知结果处理，避免重复记账。
- **旧上报。** 第一阶段保留“增加听歌时长”开关及其已有用户值，把原有 `/listen/timeadd` 的 30 分钟触发挪到实听事件，移除每分钟检查。只有当前已登录账号、明确的曲库播放可以形成上报窗口。该兼容写入也遵守前台、单飞与未知结果处理。每个账号只有一条等级时长写入路径，新接口开放时暂停旧写入，等在途请求收敛后从新的明确边界开始计。回滚同样切换边界，避免同一段时长两次写入。

### 账号、迁移和清除

- 本机新统计、云缓存与待送批次按 `API 服务来源 + userid` 隔离；未登录可播放的平台入口单列本机匿名数据。请求发送及响应落地都校验账号与会话版本。切账号、退出、换 API 地址或关闭同步时停发旧请求并丢弃失效的结果。`ApiClient` 会从响应头更新全局 session，云同步接入时还要在写 session 前检查请求归属，避免旧请求刷新新账号的凭证。切账号时不会把旧队列交给新账号发送。对应入口见 `lib/controllers/auth_controller.dart:293`、`lib/controllers/player_controller.dart:2442`、`lib/core/api_client.dart:129`。
- 旧 `playback_stats` 缺少账号归属、稳定曲目 ID 和逐段实听，迁移为只读的“本机旧版统计”。原值保留，迁移可重复执行而不累加。新的实听统计从升级时开始，历史旧版不回填酷狗。清空操作明确指向当前本机范围，序列化清除和写盘，并清理对应未送批次，已发往酷狗的记录仍由酷狗保存。异步保存完成时依据数据版本决定是否仍需补写，旧快照不能覆盖清空结果。

## 5. 性能与功耗验收

以下为首轮预算，需以同机对照结果确认。

| 场景 | 验收目标 |
|---|---|
| 锁屏暂停、停止或空闲 30 分钟 | 新统计产生 0 次周期任务唤醒、0 次请求、0 次重复落盘。状态转换允许提交一次已有脏数据。 |
| 锁屏连续播放 60 分钟 | 新统计产生 0 次独立计时器唤醒、0 次云统计请求。统计与最近历史共用约 12 次保存检查点，另计状态边界保存和已有会话快照。记录实际写入次数及字节数。 |
| 前台连续播放 60 分钟，云同步开 | 自动写入和伴随读基线合计最多 6 次，单并发，另记用户打开页面触发的读取。断网及弱网不增加同步调度次数。 |
| 万级曲目和快速切歌 | 统计采样回调 P95 < 0.2 ms，无逐次全表复制或编码。对照首播和无缝交接 P95，劣化控制在 5% 以内且不新增可听断音。前台和锁屏均覆盖。 |
| 健康播放及进程退出 | 60 分钟实听误差目标 ≤ 1%，前提是平台能提供可靠信号。暂停、seek 跳跃、缓冲等区间不应计入。正常停止后的检查点落盘，强杀在存储正常的前提下最多丢失最近约 5 分钟尚未保存的有效时长。 |
| 真机耗电对照 | Android 以相同设备、音源、音质、音效及网络做发布前后对照，每场景重复至少 3 次。覆盖锁屏离线单曲循环、流播 Wi‑Fi 和蜂窝、弱网及前台快速切歌。记录每小时 mWh、CPU 时间、唤醒、请求、写入和掉帧。首轮目标为功耗差在基线波动内，以 3% 作工程回归门槛；噪声超过门槛时延长窗口或增加轮次。 |

Android 用 Power Profiler 和 System Trace 做耗电和唤醒对照，记录整机能耗以及进程级 CPU 时间和 I/O。iOS 另跑真机锁屏与后台播放正确性及能耗回归，桌面和 Web 检查挂起、节流及恢复。

## 6. 约束与坑

- 同一首歌用两种音质播放应归到同一个有明确曲库 ID 的条目。现有 `Song.id` 可能退化成 `audio_id`、`fileid` 或 hash，数字字符串本身不足以证明是 `mixsongid`。需要在数据解析时保留来源证据，云盘及缺少曲库映射的本地条目仅计本机。已下载的曲库歌曲是否允许上报需按接口真实行为验证。参见 `lib/models/music_models.dart:456`。
- 云端所有上报以实际播放为准。`/playhistory/upload` 是否影响酷狗排行、`/listen/timeadd` 和等级查询是否共享累计值、代理批次是否确实只调用一次上游、不同设备是否覆盖写入，都需要测试账号验证。`d_sec` 短期滞后不能用来证明上一批失败。
- 采用现有音频路径，统计不通过改变 offload、音效、音质或进度采样频率来达成功耗目标。相关取舍见 [offload 与响度归一化共存评估](offload与响度归一化共存评估.md)。

## 7. 待办与上线顺序

1. **本机实听和批量保存。** 拆出可注入时钟的统计逻辑，复用播放入口，移除旧分钟计时器，迁移旧版统计。验证倍速、暂停、缓冲、seek、锁屏、换歌回滚、单曲循环、无缝切歌、快速切歌、清空和写盘并发。同步测量发布前基线及方案首轮功耗。
2. **云端只读。** 用测试账号先对照 KAmusic 默认服务端和可配置服务端的真实契约，确认等级、历史和排行的字段及刷新延迟。灰度验证离线缓存、请求合并、接口不支持、解析错误及换账号时旧响应隔离。
3. **分功能开启回写。** 历史与等级各自验证并开关，覆盖重复请求、部分成功、服务端已入账但响应超时、进程中断、批量上限、多设备并发和配额。以酷狗侧可见结果核对，超过请求或耗电预算时保持只读或按功能回滚。CSCC 起止事件在此后按实测依赖评估。
