## TL;DR

首页「电台」承载私人 FM，当前使用红心模式（`mode=normal`，推荐池 0）。进入电台时若候选为空，准备一批推荐。用户点选歌曲或按开始播放后开播。续播和锁屏控制复用 KAmusic 播放器，收藏复用酷狗「我喜欢」。登录后的个性化和反馈效果待测试账号核实。

## 1. 现状与取舍

| 方案 | 取舍 |
|---|---|
| 首页换入口，启动时把推荐塞入普通播放列表 | 改动小。有限列表、循环规则和反馈归属难以形成连续的私人 FM。 |

## 2. 首版用户体验

1. 首页第二个标签显示「电台」。进入页面准备候选，点「播放」或候选曲目后开播，离开页面后可继续播放。候选加载与重试规则见第 9、10 节。
2. 页面展示当前曲目、专辑封面和播放／暂停、下一首、红心、不喜欢。首次加载、曲库空结果、候选耗尽、离线和接口不可用各有对应状态，可用时提供「重试」或「登录」。暂停后继续当前曲目。首播失败时，现有曲目和队列继续可用。
3. 红心使用账号「我喜欢」的收藏状态。复用 `AuthController.toggleLike` 前确认收藏歌单已可用，防止其空歌单分支被当成成功。收藏成功后再按已验证的契约发 FM 反馈。推荐反馈失败时保留已成功的收藏状态。不喜欢先从本次会话排除该曲并跳过，接口确认后才视为已同步到酷狗。
4. FM 按推荐顺序续播。`上一首` 走同一会话内的有限播放历史，历史首项沿用从头播放行为。已标记不喜欢的曲目从回听路径排除。列表循环、单曲循环和随机播放设置随普通播放恢复使用。首页、迷你播放器、全屏播放器和耳机／锁屏的切歌执行同一套规则。FM 播放期间主动点播歌单或单曲，待普通播放成功后退出 FM。使用「添加到播放队列」时，在下一首优先播放手动添加的歌曲，播完回到 FM，手动添加的歌曲沿用普通统计。
5. 首版仅上线红心。后续根据真机体验和请求表现，再评估小众、30 秒速览和推荐池选择。

## 3. 播放与会话设计

**会话和接口。** 新增私人 FM 接口适配及轻量会话。会话绑定 API 配置、酷狗账号与本次启动标识。维护待播候选、当前播放项、有限历史、不喜欢集合和在途请求。推荐项显式保留曲目 ID、资源 hash、曲长及服务端推荐标记，普通播放、历史、歌词和封面继续用现有 `Song` 与音源解析。优先用可靠的曲库 ID 去重，缺失时用资源 hash；上报取接口所需的原始字段。初始上限建议为 10 个候选、20 条回听历史，另保留有容量限制的近期去重记录。缓冲留在内存，进程重启后旧快照最多按现有行为恢复暂停的曲目，新 FM 在用户主动开始时重新建会话。

**切歌和提交。** 在 `PlayerController` 统一 FM 的候选选择，将手动下一首、普通完成回调、原生无缝过界接到同一个会话。预解析只预留候选并复用现有音源预加载；成功切源或收到有效的原生过界时再消耗该候选、记录播放实例。候选补齐只追加 FM 缓冲，保留已经预备的下一首与现有播放队列版本。手动切歌与原生完成并发以播放实例和播放器既有切换归属去重。点击不喜欢可撤下匹配的预备源。遇到不可播放曲目时有限次尝试其他候选，空池或连续失败后进入可重试状态。定时停止优先于续播，并覆盖已预备原生下一首的路径。

**反馈和竞争。** 离开已提交的 FM 曲目时捕获该次播放的曲目、秒数和结束原因。手动下一首上报 `play`，不喜欢用 `garbage` 代替该次离曲的 `play`，可信的自然完播才设置完成标记。暂停、seek、换音质重载和候选预加载沿用原实例或仅更新状态。新点播意图立即作废在途切歌，普通曲目成功提交后结束 FM 会话，加载失败则允许原 FM 继续。退出账号、更换账号或 API 时立即清除旧候选并撤下预备源，当前已加载的曲目停在播放边界，用户重新开启会话后才续播 FM。归属检查要覆盖响应更新 HTTP session 的位置。过期响应不得切歌、补旧池或改当前账号状态。播放统计、历史与既有听歌时长上报仍由播放器按真实播放驱动。

## 5. 性能与功耗预算

| 场景 | 首轮目标 |
|---|---|
| 停在首页推荐、暂停或空闲锁屏 | 无页面进入或用户操作时，新增 FM 请求、独立定时器唤醒和周期写盘均为 0。 |
| 进入电台与首播 | 空池时进页与开播共用一批推荐请求，已有候选时直接复用。音源、封面请求分别统计，电台播放后仅按现有预加载策略预解析下一首。 |
| 前台与锁屏连续播放 | 候选池低水位初设 4 首，优先用离曲反馈的返回批次补齐。每次有效离曲最多 1 次 FM 动作请求，有可播候选时切歌无需等回包。候选耗尽且上次请求已结束时，当前切歌最多再尝试 1 次纯补池；若依然未获取可播放曲目，等有效播放状态变化或用户重试。自动请求单飞，失败后只在下一次实际播放事件或用户操作中检查退避。红心操作单独计数。 |
| 对照回归 | 用同设备、曲目顺序、音质、音效与网络，对照同一批歌曲的普通队列和 FM。记录首播中推荐与音源加载各自的耗时，比较有缓冲时切歌与自然交接 P95，目标劣化 ≤ 5% 且无新增可闻断音。Android 锁屏各播 60 分钟，覆盖 Wi-Fi、蜂窝与弱网；记录请求数、CPU 时间、唤醒次数和每小时耗电。首轮相对耗电回归门槛 3%，基线噪声超过该值时增加轮次。iOS 补锁屏续播与后台能耗校验。 |

## 6. 约束与坑

- 反馈 URL 走 GET，但操作具有副作用。请求已发送后超时按结果未知处理，继续使用当前缓冲。记录请求类型、业务结果和耗时供联调，省略登录凭证和用户标识。
- 自动补池与手动操作共用会话归属。切换账号、服务器或播放来源后，迟到的响应和原生过界都需要被正确处理。真机验证无缝续播、预备曲目已武装后的不喜欢及播完本曲定时停止。
- 普通队列、音质和音效行为以现有回归为准。FM 播放队列按候选和手动添加项显示；普通队列的编辑不能直接改写已武装的 FM 下一首。数据与持久化设计参考 [播放链路改进方案](播放链路改进方案.md) 和 [播放统计与酷狗云同步改进方案](播放统计与酷狗云同步改进方案.md)。

## 9. 电台页交互（2026-11-22）

**进入页面即准备候选。** 本轮实现通过 `preparePersonalFm` 准备一批推荐，复用已有候选和在途请求。`activateForBrowsing` 使候选可展示和点播，用户选歌成功后才切到 FM 播放。当前实现会在 FM 已开播时直接复用会话，开播后的空池进页规则由第 10 节定义。

| 位置 | 说明 |
|---|---|
| `lib/services/personal_fm_session.dart` | `hasCandidates` / `activateForBrowsing()` / `ensureRecommendations()` / `retryRecommendations()`；`commit(candidate)` 里用 `_adoptCandidate` 调整待播顺序。 |
| `lib/controllers/player_controller.dart` | `preparePersonalFm`（只取候选）、`playPersonalFmSong`（点选即播，成功后提交候选）、`personal_fm_select` 沿用会话的加载原因。 |
| `lib/ui/widgets/personal_fm_section.dart` | 候选行、封面、歌名共用一个点击区域；首次加载 / 空状态 / 失败重试 / 播放加载中的禁用态；横竖屏都可点选。 |

**点选顺序约定。** 点选第 N 首后，它之后的候选排在前面，原本在它前面的未播放候选移到队列末尾——既不点完立刻跳回更靠前的歌，也不静默丢弃未播推荐。离曲反馈仍只属于被离开的当前曲，未播放候选不产生任何反馈。

**失败与离线。** 解析失败时候选不被消耗、当前曲目继续可播、页面给错误提示；推荐请求失败沿用会话的单飞与退避，只有用户点「重试 / 重新获取」才会重新请求。

**不做的部分。** 「小众」「速览」仍未接入，页面也不放模式标签：没有可切换的模式就不画入口。页面离开不停播，也不启动任何轮询或周期唤醒。

**页面文案。** 只保留承担信息或操作的文字：标题「私人 FM」、卡片操作、候选区标题与数量、错误与重试。删除「边播边补」「根据你在酷狗的收听口味持续推荐」这类解释性长句、服务端下发的推荐理由、以及每行候选上的「推荐」标签（只有「插播」「回听」才真正区分来源）。

**测试。** `test/personal_fm_radio_prepare_test.dart`（自动取候选、单飞、退避、点选后的顺序）与 `test/personal_fm_section_test.dart`（进入即准备不开播、点选即播、加载中禁用、当前曲目不重复加载、横竖屏可点选）。

## 10. 收口播放行为（2026-11-23，已实现，待真机验收）

### 10.1 现状与收口范围

- 电台页已支持准备候选和点选即播。公共播放队列仍调用通用点播，播放器以曲目列表是否相等推断 FM 来源。同内容的普通歌单可能被误判，过期的 FM 条目也可能走到普通点播或插播。 [电台页](../../lib/ui/widgets/personal_fm_section.dart) · [播放队列](../../lib/ui/widgets/play_queue_sheet.dart)
- 播放器切歌提交时重建队列，会话之后还能异步合并候选。电台页和队列弹层可能显示不同内容，通用队列滑删也可能只更新快照。 [播放器](../../lib/controllers/player_controller.dart) · [FM 会话](../../lib/services/personal_fm_session.dart)
- 自动续播、原生无缝过界、空池反馈和加载回滚分别处理。需要统一离曲与提交规则，解决切歌并发、恢复暂停状态、迟到响应归属。 [播放链路改进方案](播放链路改进方案.md)

### 10.2 各入口的行为

| 操作 | 目标行为 |
|---|---|
| 进入「电台」 | 立即展示已有待播项。空池且当前没有请求或失败退避时立即取一批，即使 FM 已有当前歌曲。开播按钮与进页共用在途请求。取歌只更新候选。反复进页、重建和滚动共享同一会话与退避状态。 |
| 开始播放或恢复 | 未开播时选首个有效候选。已有 FM 曲目且暂停时恢复进度。原曲已自然完播并停在空池时，按下一首或恢复键可从新候选继续。 |
| 电台页或 FM 队列点播 | 两处按同一会话和条目身份点选。点推荐 `[A, B, C, D]` 中的 `C`，提交后待播顺序为 `[D, A, B]`。主动选新推荐时结束当前回听路径，前进项按原顺序归回可回听历史。点中前进项只消费该项，其他前进项保持相对顺序。无效条目刷新列表并保留当前播放。 |
| 点击当前曲目 | FM 播放中保持进度，暂停时恢复。若当前是普通播放，即使恰好是同一首，也按 FM 点播意图处理，提交成功才进入 FM。 |
| 普通歌单、搜索、历史、本地或下载点播 | 按普通点播处理。成功提交后退出 FM 并接管队列，失败时保留当前 FM、曲目与进度。仅准备候选的电台会话不接管普通播放器。 |
| 下一首和自然完播 | 手动插播优先，其次是回听后的前进项，最后是推荐。原生无缝过界只提交仍然有效的预备条目。FM 按会话顺序播放，退出 FM 后普通循环与随机设置继续生效。 |
| 上一首 | 回到最近实际播放的可回听曲目。历史为空时定位到开头。已标记不喜欢的歌曲从回听和前进路径排除。 |
| 添加到播放队列 | 沿用一个插播槽位，后一次添加替换前一次。允许从 FM 队列直接点播或移除此项。插播结束后继续 FM，回听时保留插播身份。 |
| FM 队列移除 | 待播推荐从本会话排除，插播和回听前进项从对应位置移除。当前曲目使用「下一首」或「不喜欢」操作。移除已预备的下一首时撤下对应原生音源。 |
| 结束电台、切换账号或 API | 主动结束使 FM 会话失效、撤下已预备音源，已提交曲目交回普通播放器。账号或 API 变化时同步废弃所属候选、未发送反馈和迟到响应，曲目由既有账号退出流程处理。 |

### 10.3 切歌、原生交接与失败恢复

1. **明确点播来源。** 普通入口继续调用 `playSong`。电台页和 FM 队列共用 `playPersonalFmSong`，点选时传入会话和条目身份，由控制器核对推荐、回听或插播来源。移除通用点播的队列内容比较和 FM 点播的普通单曲回退。补歌与移除更新同一份待播顺序，电台页、播放队列和系统媒体队列从它读取。下一首变化或失效时才撤回预备音源。
2. **只提交有效切歌。** 复用现有加载意图和原生过界检查，在解析、替换与提交边界核对会话和播放实例。显式加载成功或收到有效原生过界后，一次更新当前曲、候选、回听、队列和媒体状态。补歌可变更列表长度，已经选中的有效条目仍以身份定位。解析失败、过期点击及被取代的请求均保留候选和原顺序。
3. **约束并发。** 重复点击同一目标共用一次加载。其他入口的新明确点播可以取代尚未提交的旧意图。自然完成、原生过界和手动切歌竞争时，以当前播放实例为准只结算一次离曲。过界已经提交时，后续操作基于新曲处理。迟到的回滚也必须检查是否仍拥有当前音源。「播完本曲」优先于自动续播，包含已有预备源的场景。
4. **恢复原状态。** 解析失败且原音源仍有效时保留原音源和进度。已替换音源才按替换前的曲目、音质、进度、队列和播放／暂停状态回滚。若原曲已自然完播，失败后停在完成或暂停。自动续播遇到确定不可播的推荐时，本会话暂时排除该曲，单次续播最多再尝试一首。暂时性网络或音源错误保留候选并允许重试。

### 10.4 补歌、反馈与功耗

- **补歌。** 沿用低水位 4 首和候选上限 10 首。优先合并离曲反馈返回的曲目，有候选时直接切歌。空池自然续播先结算已完成的曲目，等待有效的反馈结果，仍为空时最多纯补一次。手动下一首遇到空池时等待在途请求或纯补一次，原曲仍在播放时等实际切走才上报。页面「重新获取」只更新候选，补歌完成后仅仍有效的续播意图可以切歌。空批或失败后进入退避，可由用户重试。
- **反馈。** 离曲时以旧曲快照捕获曲目、原始推荐来源、进度与可信的完播信息。每个真实离开的推荐播放实例最多发一次反馈，普通切歌用 `play`，可信自然完播设置 `isOverplay`，不喜欢用 `garbage`。空池导致不喜欢后无法切歌时，暂停原曲并保留本地排除，可结算这次明确的不喜欢动作。换音质、拖动、恢复音源和重放沿用当前反馈身份。插播继续按普通歌曲统计。`playtime` 先沿用已接入的进度秒数语义，手动、拖动和完播的服务端解释用测试账号核实。
- **退出。** 普通点播成功接管或主动结束时，可在原账号和 API 仍有效时发送最终离曲反馈，返回结果仅用于记录同步情况。退出账号或切换 API 时丢弃尚未发出的请求并忽略过期响应。有副作用的反馈遇到超时按结果未知处理，单次发送。
- **预算。** 进入空池页面最多发一批自动准备请求，和续播、反馈共用在途请求及退避判断。暂停、空闲锁屏和离页期间无定时取歌或周期写盘。播放时只预解析下一首。记录进页、反馈、纯补池各自的请求次数与耗时，按第 5 节做锁屏功耗对照。

### 10.5 实施顺序与验收

| 顺序 | 工作 | 验收用例 |
|---|---|---|
| 1 | 明确入口来源，统一 FM 待播和编辑 | 内容完全相同的普通歌单仍会退出 FM。普通播放中的同一首歌可以通过电台点选进入 FM。电台页和队列点选 `C` 均得到 `[D, A, B]`。补歌后弹层立即刷新，移除预备项后该曲不会被自动选中，旧会话点击保留当前播放。 |
| 2 | 统一加载提交、原生过界及失败恢复 | 覆盖快速点选、正常与重复过界、手动下一首和过界竞争、暂停时加载失败、替换失败后回滚、账号变化后的迟到响应、播完本曲定时停止。验证当前曲、真实音源、进度、媒体队列和反馈次数。 |
| 3 | 收口补歌与反馈归属 | 从首批 5 首连续播到第 6 首。覆盖 FM 已开播但空池时进页、进页与点下一首并发、反馈返回足量候选、空批、重复曲、超时、弱网和用户重试。验证请求单飞、候选充足时无需纯补池、页面重试成功后保持原播放状态，以及回听插播曲时不发送 FM 反馈。 |
| 4 | 真机验收 | Android 和 iOS 验证锁屏续播、耳机／蓝牙控制、无缝开关和断网恢复。按第 5 节记录有缓冲切歌 P95、可闻断音、60 分钟锁屏能耗与请求计数。测试账号核对 `play`、`garbage`、完成标记和秒数的接口语义。 |

自动化用例落在现有 `player_normalization_test.dart`、`play_queue_sheet_test.dart`、`personal_fm_session_test.dart` 和 `personal_fm_radio_prepare_test.dart`。队列组件测试验证实际按钮走正确入口，控制器测试以可控完成事件、过界事件和失败回包覆盖状态切换。

### 10.6 实施记录

- 电台页和播放队列共用 FM 会话条目。补歌与移除即时同步媒体队列，待播首项变化时撤下旧预备音源。普通点播提交后退出 FM，结束电台后当前歌曲保留在普通播放器。
