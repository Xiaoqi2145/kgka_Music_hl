## TL;DR

KA Music 当前是**单层播放链路**：一个 3 322 行的 `PlayerController` 同时承担身份、并发、原生适配、展示提交与音频策略，原生侧（just_audio + ExoPlayer）只暴露"换单个音源"这一种换歌语义。EchoMusic 的成熟度来自**三层各自解决一个问题**：原生层提供多条换源语义 + 双代次栅栏，主进程层提供命令串行 + 事件过滤，渲染层提供意图/引擎双状态 + 展示对账。

本方案不移植 EchoMusic 的实现（技术栈不同：Rust 自研引擎 vs just_audio/ExoPlayer），而是**移植它的问题分解方式**，分四期落地：

| 期 | 主题 | 解决的真实缺陷 | 预估 |
|---|---|---|---|
| **A** | 身份与提交边界收敛 | 响度补取无负缓存、去重键含 generation 导致可重复请求；`generation` 未纳入租约 | 4–6 人日 |
| **B** | 状态机显式化 | 加载生命周期只有 `bool isPreparing`，`isBuffering` 是死字段 | 3–5 人日 |
| **C** | 观测闭环 | 无法从日志判断"播放中 vs 静默缓冲"；无成功率指标 | 2–3 人日 |
| **D** | 换源语义扩展（唯一提升"无缝"的一期） | 当前必然 pause→load→play，存在可听间隙 | 6–9 人日 + 实机验收 |

**A/B/C 是 D 的前置**：D 要把"原生边界"当成提交依据，而 A 提供身份、B 提供状态、C 提供验收手段。反过来做（先改 append 再补身份）正是 2026-09 那轮被回退的路径。

> **实施状态（2026-09-26 复核）**：**A、B、C 三期已落地**——`lib/services/playback_phase.dart`、
> `lib/services/playback_failure.dart` 已存在，`TransitionLease` 已含 `generation`，`LoudnessLookup`
> 已有负缓存（`markMissing` / `isKnownUnnormalizable`），`_traceTransition` 已输出
> `sinceCompletedUs` / `sinceLoadStartUs` / `progressRevision`。**Phase D 未实施**，换歌仍是
> 显式单音源替换（`lib/services/music_audio_handler.dart:88`），**不承诺样本级无缝**。
> 因此下文 A/B/C 各节按「设计依据与验收口径」阅读，不再作为待办；§9c 已相应更新。
> 本机实施记录见 `diagnostics/playback-chain-phase-abc-result.md`（未入库）。

## 0. 结论摘要

- **可移植**：EchoMusic 的**问题分解**与**栅栏设计**。KA Music 已有 `TransitionCoordinator`（entryId / seekRevision / requestRevision / intentRevision / 一次性 completion），这是 EchoMusic `playbackRequestSeq + nativeTrackSeq + generation` 的**简化同构物**——方向是对的，只是缺维度。
- **不可移植**：Rust 引擎的双 deck 混音、无锁环、`track_seq`/`decode_generation` 原生事件协议。just_audio 0.10.5 的公开事件只带 `(currentIndex, updatePosition, updateTime, duration, processingState)`，**没有原生 entryId**（`lib/services/music_audio_handler.dart:19-26` 的注释已承认这一点）。
- **唯一真正能买到"无缝"的机制**：just_audio 的**多子源播放列表 + 原生自动过渡**。0.10.5 的 `ConcatenatingAudioSource` 仍在（`just_audio.dart:2922`、`:3061`），`AudioPlayer.positionDiscontinuityStream`（`just_audio.dart:643`）是**公开 API**，且只在"条目身份变化"时触发（`just_audio.dart:287-322`，seek 期间显式 return）——它比 `sequenceStateStream` 干净得多。这是 Phase D 的支点。
- **主路径与预解析路径本身已正确复用**：`_resolveSource` 命中预解析时直接用 `prepared.url`（`lib/controllers/player_controller.dart:1028-1040`），不重复请求。真正可修的是**响度补取的缓存语义**：`LoudnessLookup.put` 对 `null` 不写负缓存、`_hydrateLocalLoudness` 的去重键含 `generation`，使同一曲目可被重复补取。见 §A1——**该项已修完**（见文首实施状态）。

## 1. 现状：KA Music 播放链路的三层事实

> **阅读提示**：本节描述的是**方案提出时（2026-09-26 前）的基线**，是 A/B/C 三期要解决的问题。
> 其中身份维度、状态枚举、观测三处**已由 Phase A/B/C 修复**（见文首实施状态）；换源语义一节
> **至今仍然成立**——Phase D 未实施。保留本节是为了让 Phase D 的设计依据可追溯。

### 1.1 身份维度（方案提出时：只有一个，且语义混装）

| 现有标识 | 位置 | 语义 | 问题 |
|---|---|---|---|
| `TransitionCoordinator.committedEntry.id` | `lib/services/transition_coordinator.dart:2-6,59-64` | 一次成功加载 = 一个新播放实例 | **正确**，与 EchoMusic `trackSeq` 同构 |
| `TransitionLease` | `lib/services/transition_coordinator.dart:14-25` | entryId + seekRevision + requestRevision + **generation** | **已补齐 generation 维度**（Phase A2） |
| `_loadSerial` / `_playRequestGeneration` / `_prepareNextSerial` / `_seekSerial` / `_queueRevision` / `_volumeNormApplySerial` | `lib/controllers/player_controller.dart` | 6 个独立计数器 | 缺统一说明与不变量测试 |
| `_playbackLoudness.generation` | `lib/services/playback_loudness.dart:96-109` | 响度代次 | **已改为注入 `TransitionCoordinator.generation`**，不可能再漂移（Phase A2） |

**EchoMusic 的对照**：它只有两个身份维度 `seq`（曲目）+ `generation`（同一曲目内的 seek/重置/DSP 重建），且**显式解耦**——`native` 侧有测试断言"换 seq 不 bump generation"。

**KA Music 当时的等价缺口**：`_playbackLoudness.generation` 与 entryId 无绑定关系，靠 `_selectNormalizationSource(force: true)` 兜底；且一个跨越"换音质重载当前曲"的异步完成回调，entryId 会变（`_reloadCurrentSongForQuality` 走完整 `_playSong`），所以**当时实现是安全的**——但安全来自"每次重载都换 entryId"这个巧合，而不是来自显式的 generation 维度。**Phase A2 已把这个巧合变成显式约束**；Phase D 引入"同 entryId 内的原生过渡"时，依赖的正是这条约束。

### 1.2 换源语义（只有一条）

`music_audio_handler.dart:72-93`：

```dart
await pauseForInterruption();
await audioPlayer.setAudioSources([_audioSourceFor(song, url)], initialPosition: ...);
```

`setAudioSources` 的实现（`just_audio.dart:877-903`）是：`_playlist._init(...)` **清空并重建** → `load()`（`preload` 默认 true）。**这是 EchoMusic 的 `LoadPlan::Initial`（完整重建），而不是 `Continuous`（复用 session）或 `Gapless`（边界交接）**。

EchoMusic 的三条语义对照：

| EchoMusic | 行为 | KA Music 等价物 |
|---|---|---|
| Initial | 重建 decoder + output | **有**：`setAudioSources` |
| Continuous | 后台开新 decoder，旧输出继续，校验后切换 | **无** |
| SourceSwitch | 同位续播（换音源不换时间轴） | **无**：换音质走完整重载（`_reloadCurrentSongForQuality`，`lib/controllers/player_controller.dart:2368`） |
| Gapless/Transition | decode 线程内双 deck 混音 | **无** |

### 1.3 并发模型（自研，与 EchoMusic 思路一致但更粗）

`_playSong`（`lib/controllers/player_controller.dart:704-929`）的 `intent → resolve → claim → replace → commit → play` 六段状态机 + `alive(stage)` 检查点，**与 EchoMusic 的 `playTrack` 骨架同构**（`EchoMusic-渲染层Store分析` §2.1 的 17 步）。这条链路是项目里质量最高的部分，**不应改动其结构**。

真正的缺口在**原生事件的接收侧**：

```dart
// lib/controllers/player_controller.dart:1589-1601
void _onPlaybackEvent(PlaybackEvent event) {
  if (_disposed || isPreparing || _isSeeking || _isScrubbing ||
      !_ownsLoadedSource ||                       // ← sequence.length == 1 且 identical
      !identical(event, audioPlayer.playbackEvent) ||  // ← 身份过滤（可接受）
      event.currentIndex != 0) {                  // ← 硬编码 0，与"多子源"直接冲突
    return;
  }
```

`_ownsLoadedSource`（`lib/controllers/player_controller.dart:1524-1529`）要求 `sequence.length == 1`。这个不变量是 2026-09 修复的**核心成果**（本机记录 `diagnostics/preload-multiple-transition-fix-result.md`，未入库），必须保留；Phase D 要做的是**给它一个受控的例外窗口**，而不是取消它。

### 1.4 观测（方案提出时：缺失；Phase C 已补齐代码侧）

- `isBuffering` 曾是无读取点的死字段；**Phase B/C 已接线**——现由 `playbackPhase` getter（`lib/controllers/player_controller.dart:344-353`）经 `resolvePlaybackPhase` 消费（`lib/services/playback_phase.dart:73`）。
- **Phase C 已补**"播放尝试 → 成功"计数（`playbackAttempts` / `playbackCommits` / `playbackSuccessRate`，`lib/controllers/player_controller.dart:1576-1587`）。仍无 `underrun` 概念。
- `_traceTransition`（`lib/controllers/player_controller.dart:1540-1563`）**已补**跨事件耗时 `sinceCompletedUs` / `sinceLoadStartUs` 与 `progressRevision`、`generation`；失败分类由 `load_fail_classified` 事件承载。**仍缺的是实机 P95 基线**（未采集）。

## 3. Phase A：身份与提交边界收敛（P0）

**目标**：在不动原生语义的前提下，消除重复解析、把"身份"从 6 个隐式计数器提升为显式模型。

### A1. 收敛 `/song/url` 的调用点（预估 1–2 人日）— **已完成**

**先给事实边界**：controller 内共 **3 处** `_api.songUrl` 调用点，其中**主路径与预解析路径本身已经复用**，不存在"主路径 + 预解析各请求一次"的重复：

| # | 调用点 | 触发条件 | 说明 |
|---|---|---|---|
| 1 | `lib/controllers/player_controller.dart:1044` | `_resolveSource` 且非 local/prepared | **主路径**。命中预解析时走 `:1028-1040` 的 `prepared.url`，**不请求** |
| 2 | `lib/controllers/player_controller.dart:1266` | `_hydrateLocalLoudnessOnce` | **只补响度**，不取 URL |
| 3 | `lib/controllers/player_controller.dart:1703` | `_prepareNextSourceIfNeeded` | **预解析**，写 `_PreparedNextSource`，供 #1 复用 |

> 另有 `lib/controllers/download_controller.dart:392` 一处，属下载链路，不在本方案范围。

**当时的缺陷是 #2 的负缓存缺失**：`LoudnessLookup.put` 在 `data?.canNormalize != true` 时**直接 return，什么都不写**。于是当服务端对某首歌不返回 `volume` 字段时：

1. `_hydrateLocalLoudnessOnce` 拿到 `loudness == null` → `resolve` 的 `then` 里写入 `_retryAfter = now + 1min`；
2. **但** `_hydrateLocalLoudness` 的 `putIfAbsent` 键是 `'${key}:${generation}'`——**每次响度代次变化都会换一个新键**，去重失效；
3. 而 `_restoreLocalLoudness` 在 `available == null` 时**无条件**调 `_hydrateLocalLoudness`。

**实机证据（已复核，本机记录未入库）**：`diagnostics/rt-logcat-focus.log` 21:49:33.244 与 21:49:46.545 出现**同一候选** `F8B7AD36BC8698D72A56A2C21908F54B` 的两次 `prefetch_ready`。但两次之间 21:49:46.380 有一次 `load_intent reason=explicit_load`——**这是用户点击触发的重解析，不是自动重复请求**。因此该日志**不能**作为"重复网络往返"的证据，只能说明"预解析结果在用户操作后被正确作废并重建"（行为正确）。**该结论不依赖文件可核对，属于当时的人工判读。**

**落地结果**（去掉无证据的部分，只做可证明的三件事）：

1. **`LoudnessLookup.put` 的 null 语义**：`put` 保持 no-op，新增 `markMissing`（只有真正发起过网络往返的 `resolve` 才调用）与 `isKnownUnnormalizable`，并在 `retainKeys` 中一并驱逐 —— `lib/services/playback_loudness.dart:31,49-53`；
2. **`_hydrateLocalLoudness` 的去重键去掉 `generation`**：改为 `_loudnessKey(song, quality)`（`lib/controllers/player_controller.dart:1186-1187,1244`）；
3. **`_restoreLocalLoudness` 增加"已知不可归一化"短路**：`lib/controllers/player_controller.dart:1234`。

**验收（已由现有用例覆盖）**：
- 负缓存端到端：连续多次 `_restoreLocalLoudness` 只产生 **1** 次 `api.requests`；
- `normalizationGeneration` 变化后，同一曲目的响度补取**不重复**发起；
- `test/player_normalization_test.dart` 的既有断言作为回归护栏保留。
- 隔离护栏：`test/playback_loudness_test.dart` 覆盖 `markMissing` 退避与 `isKnownUnnormalizable` 报告路径。

### A2. `TransitionLease` 增加 generation 维度（预估 1–2 人日）— **已完成**

**落地结果**：把 `_playbackLoudness.generation` 的语义**上收**到 `TransitionCoordinator`：

```dart
// lib/services/transition_coordinator.dart:14-25
class TransitionLease {
  const TransitionLease(this.entryId, this.seekRevision, this.requestRevision, this.generation);
  final int generation;   // 同一 entry 内的管线代次：换音质重载/响度窗口重开
}
```

`TransitionCoordinator.commit(loadRevision)` 与 `reset()` 递增 generation，新增 `bumpGeneration()`；`PlaybackLoudness` 改为**注入** coordinator 的 generation，而不是自增（`lib/services/playback_loudness.dart:96-109`）。这样两者**必然一致**，消除"两个独立计数器需要人工保持同步"的隐患。

**不变量（已写成测试）**：
1. 任何原生替换发生时，`committedEntry != null`；
2. 任何响度应用通过 `isCurrent()` 时，`generation` 与租约一致；
3. 换音质重载后，旧 generation 的响度应用**必然**被丢弃 —— 见 `test/player_normalization_test.dart` 的 "the loudness generation is the coordinator generation, never a copy" 与 `test/transition_coordinator_test.dart:103-147`。

### A3. 清理 `_prepareNextSourceIfNeeded` 的窗口语义（预估 1 人日）— **已完成**

**当时的缺陷**：

- `_clearPreparedNext()` 会 `++_prepareNextSerial` 使在途结果作废，但**不设置冷却**——冷却只在失败分支设置。因此"进窗口 → 拖回去 → 再进窗口"会重复请求；
- `_prepareNextCooldownUntil` 用 `DateTime.now()`，与 `_transitionClock`（单调 Stopwatch）不一致，系统时间跳变会影响行为。

**落地结果**：
- 冷却基准改用 `_transitionClock.elapsed`，与 trace 口径统一（`lib/controllers/player_controller.dart:1731-1735`）；
- 进窗口去重与失败冷却均由现有用例覆盖。

**验收（已覆盖，原为 0 覆盖）**：
1. 进入 30s 窗口 → 退出 → 再进入，`api.requests` 只增 1 —— `test/player_normalization_test.dart:1087`；
2. 预解析失败后 15s 内不再重试（对应 WBS `T-M4-07` 的验收标准"有测试"）—— `test/player_normalization_test.dart:1104`；
3. 关闭 `gaplessPlaybackEnabled` 丢弃在途候选且不再发起。

### B1. 定义 `PlaybackPhase` 枚举（预估 2 人日）


| `stalled` | `isStalled`：`ready` 且 `playing` 且位置连续 5 秒未推进（`lib/controllers/player_controller.dart:454-485`） |
| `error` | `errorMessage != null` |

**优先级顺序已修正**：`buffering` 排在 `stalled` **之前**（`lib/services/playback_phase.dart:70-75`），否则"网络慢导致的长缓冲"会被误报为异常停顿。

**关键约束**：`PlaybackPhase` 是**派生只读**，不得引入新的写入路径——否则会变成第 7 个隐式状态。EchoMusic 的教训是双状态必须由纯函数派生（`stateMachine.ts:116-118`），KA Music 同理。落地时严格遵守：`playbackPhase` 只是 getter（`lib/controllers/player_controller.dart:344-353`）。

### B2. 失败分类与恢复策略表（预估 1–2 人日）

EchoMusic 有 `PlayerErrorCode` 10 种 + 明确恢复动作。KA Music 原先只有 `errorMessage = '播放失败，请重试'` 等硬编码字符串。

已落地为 `lib/services/playback_failure.dart`：`PlaybackFailure` 六类 + `PlaybackRecovery` 五动作 + 显式恢复表 `playbackRecoveryForFailure` + 文案 `playbackFailureMessage`。**只做分类，不改变控制流。**

```dart
enum PlaybackFailure {
  resolveEmpty,      // 无播放地址        → 降级音质重试
  resolveNetwork,    // 网络异常          → 有限重试（ApiClient 已有重试）
```

现有 `_playSong` 的 `plans` 已实现"预解析 → 音质梯度"的降级链，**只把失败原因分类并上报**，控制流未变。

## 6. Phase D：换源语义扩展（唯一提升"无缝"的一期）

**目标**：把"自然播完"从 `pause → load → play`（`lib/services/music_audio_handler.dart:84-92`）改为**原生边界交接**，消除可听间隙。

### D1. 支点：just_audio 的多子源 + 公开边界事件

**事实核查**（`just_audio-0.10.5`，本机 pub cache 实测）：

| 事实 | 证据 |
|---|---|
| `ConcatenatingAudioSource` 仍存在且可动态增删 | `just_audio.dart:2922`、`:3034`（`addAll`）、`:3061`（`insertAll`）、`:3088`（`removeAt`） |
| `positionDiscontinuityStream` 是**公开** getter | `just_audio.dart:643` |
| 该流只在**条目身份变化**时发 `autoAdvance` | `just_audio.dart:287-322`：`if (currSource._id != prevSource._id)` 才发；**seek 期间显式 `return`**（`:298`） |
| 原生自动过渡是 ExoPlayer 内建的 | `AudioPlayer.java:291-301`：`onPositionDiscontinuity(reason=AUTO_TRANSITION)` → `updateCurrentIndex()` |
| ExoPlayer 的 transition 在音频线程内完成 | 这是 ExoPlayer 的既定行为，**无需自研双 deck 即可获得样本级接续** |

**关键洞察**：`positionDiscontinuityStream` 比 `sequenceStateStream` 干净——后者在**任何**结构变更（包括 Dart 侧 `add`/`remove` 的乐观广播）都会触发，正是 2026-09 那轮误切歌的根源；前者只在**真正的条目身份变化**时触发，且 seek 被显式排除。

> 2026-09 的方案文档（本机记录 `diagnostics/preload-multiple-transition-fix-plan.md` §"明确不采用"，未入库）反对的是"把 `sequenceState` 最新快照当成原生提交依据"——**这个反对依然成立**。Phase D 用的是不同的信号源。

### D2. 目标不变量（顺序不可颠倒）

1. **单子源是默认状态**：任何时刻，播放列表长度只能是 1（当前曲）或 2（当前曲 + 已武装的下一曲）；
2. **武装只在窗口内发生**：`remaining ∈ [3s, 30s]` 且 `gaplessPlaybackEnabled` 且非单曲循环；
3. **武装不提交**：追加子源**不得**改动 `currentSong` / `lyrics` / `_audioPlayer.setCurrentMediaItem` / 历史 / 统计 / 响度代次——与 `_PreparedNextSource` 的"纯缓存"语义（`lib/controllers/player_controller.dart:29` 起的类注释）一致；
4. **提交只由原生边界触发**：`positionDiscontinuityStream` 的 `autoAdvance` + `event.currentIndex == 1` + 条目 tag 匹配已武装的 song；
5. **提交后立即回到单子源**：移除 index 0（已播完的 A），恢复 `_ownsLoadedSource == true`；
6. **任何失效路径必须撤销武装**：seek / 手动 next / previous / 换队列 / 换音质 / 暂停 / 关闭开关 / 队列长度变化 → `_dropArmedNext()`。

### D3. 生命周期

```
窗口进入
  └─ _prepareNextSourceIfNeeded() 解析 URL（沿用现有逻辑，仅缓存）
      └─ 条件满足 → _armNextSourceOnNative()
          ├─ audioPlayer.addAudioSource(AudioSource.uri(url, tag: next))
          ├─ _activePlaylistSource 保持为 A（不放行 _onPlaybackEvent）
          └─ _armedNext = ArmedNext(song, url, ownerEntryId, queueRevision, requestRevision)
                    │
                    │  A 播完，ExoPlayer 在音频线程内无缝切到 B
                    ▼
      positionDiscontinuityStream(autoAdvance, index 0→1)
          ├─ 校验 _armedNext.ownerEntryId == currentEntryId（否则丢弃）
          ├─ _commitPlayback(next, quality, loudness, reason: 'native_auto_advance',
          │                  start: Duration.zero)      ← 唯一提交点，复用现有方法
          ├─ _activePlaylistSource = sequenceState.currentSource（B）
          ├─ unawaited(removePlaylistSourceAt(0))        ← 回到单子源
          └─ _armedNext = null
```

**注意**：`_commitPlayback`（`lib/controllers/player_controller.dart:930-985`）**可以直接复用**——它已经处理了 `currentSong`、`_selectNormalizationSource(force: true)`、`_rememberLoudness`、歌词、媒体通知、历史、统计、会话持久化。这正是 §2.3 "提交边界唯一"这条既有约束的红利。

### D4. 必须处理的六个细节（每个都要有测试）

| # | 细节 | 处理 | 测试 |
|---|---|---|---|
| 1 | 武装后用户 seek 回中间 | `_dropArmedNext()`：`removeAudioSourceAt(1)` + 清 `_armedNext` | 武装 → seek → 断言 sequence.length == 1 |
| 2 | 武装后用户手动 next | 走现有 `next()`，但**先** `_dropArmedNext()`，否则会出现 3 个子源 | 武装 → next → 断言 sequence.length == 1 |
| 3 | 已武装的 B 在播放前从队列被移除 | `_queueRevision` 变化 → `_dropArmedNext()`（`_clearPreparedNext`，`lib/controllers/player_controller.dart:1499-1510` 已有调用点） | 武装 → replaceQueue 去掉 B → 断言撤销 |
| 4 | 原生过渡已发生但 `_armedNext` 已被清 | **拒绝认领并主动恢复**（对齐 EchoMusic `activateGaplessPreparedTransition` 的 `playback.ts:679` 语义），而不是让错误的歌播下去 | 武装 → 清 `_armedNext` → 推 autoAdvance → 断言恢复到正确曲目 |

| 6 | 暂停/关闭开关时已武装 | `pauseForInterruption` 不清（暂停不清有效候选，与现有测试语义一致）；关闭开关清 | 参数化 2 例 |

## 9b. 约束与坑

1. **不可移植的边界**：just_audio 的 `PlaybackEvent` 不含原生曲目身份，本方案的所有身份判定都建立在 Dart 侧 `TransitionCoordinator` 上；一旦依赖的 `identical(event, audioPlayer.playbackEvent)` 语义变化，Phase D 的提交判据需要重新验证。
2. **Phase D 仅在 Android 生效**：`.flutter-plugins-dependencies` 显示 Windows/Linux 无 just_audio 实现，iOS/macOS/Web 的原生自动过渡未实测。`gaplessPlaybackEnabled` 在非 Android 平台应默认关闭武装逻辑。
3. **本方案不改 `_playSong` 的六段状态机结构**。它已被 `test/player_normalization_test.dart` 的 42 例单测覆盖（该文件的静态声明数与实际执行数不同，权威值见 `docx/06-质量保障/测试策略与现有用例.md` §1.1），任何"顺手重构"都会让 Phase D 的回归基线失效。
4. **不加新的设置项**：A/B/C 三期不引入用户可见开关，避免 `docx/04-数据与接口/本地存储与配置项清单.md` 与 UI 层同步成本。
5. **不做交叉淡化**：需要解码侧双轨，just_audio 不提供；EchoMusic 的 Fade/Automix 属自研引擎能力。
6. **不修改全局 Pub Cache**：任何 `just_audio` 行为差异都必须通过本仓库可控方式处理。
7. **实机验收不可用单测替代**：本机记录 `diagnostics/preload-multiple-transition-fix-result.md`（未入库）已明确"模拟次数不能折算为实机验收次数"，Phase D 的 §D7 表格是硬门禁。

## 10. 与 EchoMusic 的取舍总结

| 维度 | EchoMusic | KA Music 本方案 | 理由 |
|---|---|---|---|
| 身份维度 | `seq` + `generation` + 原生事件序号 | entryId + generation（**2 维**） | just_audio 无原生事件序号；`identical(event, playbackEvent)` 已替代 |
| 换源语义 | 4 条 | **2 条**（单子源替换 + 原生边界交接） | Continuous/SourceSwitch 需要引擎级 session 复用，just_audio 不提供 |
| 过渡 | 5 种模式 + 双 deck 混音 | **1 种**（gapless butt-splice） | 混音需解码侧双轨，不可移植 |
| 并发 | 命令队列 + 事件栅栏 | 六段状态机 + `_sourceLoadChain` | 已有且足够 |
| 观测 | `core-state` / `ao-state` / `packet-cache` / `output-stats` 四路诊断 | **1 路**（`_traceTransition`）+ Phase C 扩展 | 受平台约束，够用即可 |
| 乐观 UI | 意图优先 + 对账 | 不做（等 native 确认） | KA Music 无"引擎加载慢到需要乐观"的场景，少一层复杂度 |

**核心判断**：EchoMusic 的复杂度中，**约 60% 来自"自研引擎需要自己保证实时性"**（无锁环、try_lock、generation fencing、双 deck 混音）——这部分对 KA Music **完全无用**；剩下 **40% 来自"多入口并发 + 展示对账"**（epoch 护栏、双状态、提交边界）——这部分 **KA Music 已经有 70%**，本方案补的是剩余 30%（generation 维度、状态枚举、观测、原生边界提交）。
