# 工程化推进总纲

## TL;DR

项目功能已经「能跑且功能丰富」，但工程化程度停留在**个人项目水平**：无 CI、无崩溃上报、无发布签名、测试覆盖率 3.7%、单文件最大 3 537 行。推进策略是**先立基线、再补质量、后拆架构**——顺序不可颠倒，因为架构重构若无测试与门禁保护，等于在流沙上盖楼。全程分 8 个里程碑（M0–M7），预计 20 个迭代（2 周/迭代），核心量化目标是：测试覆盖率 ≥ 30%、最大单文件 ≤ 600 行、发布门禁 100% 可自动执行。

---

## 1. 现状评估（工程成熟度）

按 5 个维度打分（1 分=缺失，2 分=临时方案，3 分=有规范但靠自觉，4 分=有自动化保障，5 分=持续改进）：

| 维度 | 得分 | 依据 |
|---|---|---|
| 构建与发布 | 1.5 | 无签名配置、无 CI、版本号手工同步 |
| 质量保障 | 1.5 | 测试 7 文件 / 1 239 行 / 52 例；`analysis_options` 仅默认 lint；无崩溃上报 |
| 架构与可维护性 | 2.0 | 分层干净，但最大文件 3 537 行、控制器 120+ 成员 |
| 可观测性 | 1.0 | 仅 `debugPrint`，无结构化日志、无指标、无错误上报 |
| 工程纪律与文档 | 1.5 | 有 README/update.md，但无提交规范、无评审清单、无门禁 |
| **综合** | **1.5 / 5** | **「可用的原型」，尚未达到「可交付产品」** |

目标：**20 个迭代后综合 3.5 / 5**（有规范、有自动化、有度量，但尚未形成持续改进闭环）。

## 2. 推进原则

| 编号 | 原则 | 说明 | 反例 |
|---|---|---|---|
| P-01 | **先测量，后优化** | 任何性能/质量优化前必须先有基线数据，否则无法判断是否有效 | 「感觉快了」 |
| P-02 | **先加护栏，再拆房子** | 架构重构前必须先有测试与门禁；无护栏的重构一律拒绝 | 直接重写 `PlayerController` |
| P-03 | **小步快跑，每次可回滚** | 单个 PR 只做一件事，可独立回滚 | 一个 PR 同时拆文件 + 改逻辑 |
| P-04 | **契约先行** | 涉及接口/存储/平台能力的改动，先写方案与文档，再写代码 | 直接改 API 参数 |
| P-05 | **不留半成品** | 不允许「先注释掉」「先 TODO」「下个迭代再说」长期悬挂 | `// TODO: 后面处理` |
| P-06 | **纪律优先于速度** | 门禁不通过不合并；宁可延后，不可带病发布 | 跳过 analyze 提交 |

## 4. 里程碑依赖关系

```
M0 基线固化
 ├─▶ M1 质量地基
 │     └─▶ M2 架构解耦
 │           └─▶ M3 数据与缓存治理
 │                 └─▶ M4 播放内核加固
 │                       └─▶ M6 体验与性能
 ├─▶ M5 跨平台与发布（可与 M2/M3 并行，但依赖 M1 的门禁）
 └─▶ M7 工程可持续（依赖 M1–M5 的产出）
```

| 约束 | 说明 |
|---|---|
| M1 必须先于 M2 | 无测试保护的架构重构风险不可控 |
| M1 必须先于 M5 | 发布流程必须建立在自动化门禁之上 |
| M3 必须先于 M4 | 播放内核加固需要稳定的缓存层 |
| M7 最后 | 流程闭环需要前面所有里程碑的实际数据 |

## 5. 各里程碑目标与验收

### M0 基线固化（2 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 把「当前是什么样」写成可核对的事实，并让构建/检查可重复执行 |
| **DoR** | 代码库可编译；有可用的 Flutter 环境 |
| **交付物** | 本知识库全部文档；`docx/` 索引；技术债台账；本地门禁脚本；版本号同步脚本 |
| **DoD** | ① 门禁脚本 `scripts/check.ps1` 可在本地一键跑通；② 台账 38 条全部有证据与验收方式；③ 文档索引无死链；④ 版本号三处一致校验通过 |
| **风险** | 文档工作量被低估 → 用「先骨架后填充」策略，允许 L1 契约先占位 |

### M1 质量地基（3 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 让每次改动都有自动化正确性检查 |
| **DoR** | M0 完成，门禁脚本可用 |
| **交付物** | 收紧的 `analysis_options.yaml`；本地门禁脚本；CI 流水线；崩溃/错误上报；关键路径单测 |
| **DoD** | ① `flutter analyze` 零警告；② `flutter test` 全绿且覆盖率 ≥ 30%；③ CI 在 PR 上自动运行并阻断；④ 播放链路与缓存链路有单测；⑤ 错误上报能收到一条真实异常 |
| **风险** | 收紧 lint 会产生大量存量告警 → 分批开启，先 `warnings-as-errors` 只针对新增代码 |

### M2 架构解耦（3 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 消除巨型文件，显式化依赖 |
| **DoR** | M1 完成，播放与缓存有测试保护 |
| **交付物** | 拆分后的 `player_page` / `player_controller` / `music_models` / `music_api`；依赖规则检查脚本；DI 收敛 |
| **DoD** | ① 最大单文件 ≤ 600 行；② 分层依赖脚本门禁通过；③ 拆分过程零行为变更（对比测试/录屏）；④ 公开 API 未破坏 |
| **风险** | 拆分引入回归 → 每个 PR 只拆一个文件，拆分前后功能对照测试 |

### M3 数据与缓存治理（3 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 四套存储统一抽象，关闭缓存类技术债 |
| **DoR** | M1、M2 完成 |
| **交付物** | `DiskCache` 统一接口；迁移到 ApplicationSupportDirectory；低水位淘汰；失败缓存；存储键注册表 |
| **DoD** | ① TD-01/02/05/06/09/18/23/24 关闭；② 缓存相关单测覆盖淘汰与并发；③ 系统清缓存后离线内容仍可用 |
| **风险** | 目录迁移可能丢用户缓存 → 保留旧目录一次性搬移，失败回退 |

### M4 播放内核加固（3 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 播放状态可穷举、错误可恢复、效果可度量 |
| **DoR** | M3 完成 |
| **交付物** | 播放状态机；错误分类与恢复策略表；音质降级策略可配置；音量与均衡交互模型；离线 LUFS 方案评估 |
| **DoD** | ① 播放状态机有单测；② 播放失败率可从日志统计；③ TD-12/13/36 关闭或明确接受；④ 后端 LUFS 透传问题有结论 |
| **风险** | 状态机改动面大 → 保留旧路径开关，灰度验证 |

### M5 跨平台与发布（2 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 具备正式分发能力 |
| **DoR** | M1 完成 |
| **交付物** | release 签名配置；多 ABI 构建；发布检查清单；应用内更新链路加固；平台差异矩阵 |
| **DoD** | ① release 产物使用正式证书；② `arm64-v8a + armeabi-v7a` 构建通过；③ 发布流程可一键执行；④ TD-03/16/17 关闭 |
| **风险** | 密钥管理不当 → 密钥不入库，使用 `key.properties` + 环境变量 |

### M6 体验与性能（2 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 性能与体验达到可度量基线 |
| **DoR** | M1、M4 完成 |
| **交付物** | 性能基线报告；启动优化；图片解码优化；列表虚拟化；本地音乐增量扫描 |
| **DoD** | ① 冷启动、首屏、滚动帧率达标（见性能基线文档）；② TD-15/34/35 关闭或明确接受；③ 包体积不超过基线 +10% |
| **风险** | 优化无收益 → 每个优化点先测量、后改动、再测量 |

### M7 工程可持续（2 迭代）

| 项 | 内容 |
|---|---|
| **目标** | 流程闭环，可多人协作 |
| **DoR** | M1–M5 完成 |
| **交付物** | 贡献者指南；PR/评审流程；安全与合规整改；文档健康度机制 |
| **DoD** | ① 新贡献者按指南可在 1 天内跑通并提交 PR；② 文档健康度 100%；③ TD-30/31/32 关闭；④ 季度校验机制落地 |
| **风险** | 单人维护缺乏动力 → 用自动化替代人工巡检 |
