# 工程化推进总纲

> **指标口径**：本文出现的代码规模、测试数、覆盖率、技术债数、静态分析违规数
> **一律引用 `06-质量保障/`**（权威单点见 `../06-质量保障/测试策略与现有用例.md` §0），
> 本文不复制数值，避免代码变更后多文档漂移。

## TL;DR

项目功能已经「能跑且功能丰富」，但工程化程度停留在**个人项目水平**：无 CI、无崩溃上报、无发布签名、全项目行覆盖率约 3%（口径见 `06-质量保障/`），最大单文件行数见 `01-项目总览/目录结构与文件地图.md` §3.1。推进策略是**先立基线、再补质量、后拆架构**——顺序不可颠倒，因为架构重构若无测试与门禁保护，等于在流沙上盖楼。全程分 8 个里程碑（M0–M7），预计 20 个迭代（2 周/迭代），核心量化目标是：测试覆盖率 ≥ 30%、最大单文件 ≤ 600 行、发布门禁 100% 可自动执行。

## 1. 现状评估（工程成熟度）

按 5 个维度打分（1 分=缺失，2 分=临时方案，3 分=有规范但靠自觉，4 分=有自动化保障，5 分=持续改进）：

| 维度 | 得分 | 依据 |
|---|---|---|
| 构建与发布 | 1.5 | 无签名配置、无 CI、版本号手工同步 |
| 质量保障 | 1.5 | 测试规模见 `06-质量保障/测试策略与现有用例.md` §1.1（L5 仅 3 例、L6 为 0）；`analysis_options.yaml` 仅默认 lint；无崩溃上报 |
| 架构与可维护性 | 2.0 | 分层干净，但最大单文件与控制器规模偏大（数值见 `01-项目总览/目录结构与文件地图.md` §3.1、`03-模块详解/控制器层-PlayerController.md` §1） |
| 可观测性 | 1.0 | 仅 `debugPrint`，无结构化日志、无指标、无错误上报 |
| 工程纪律与文档 | 1.5 | 有 README/update.md，但无提交规范、无评审清单、无门禁 |
| **综合** | **1.5 / 5** | **「可用的原型」，尚未达到「可交付产品」** |

目标：**20 个迭代后综合 3.5 / 5**（有规范、有自动化、有度量，但尚未形成持续改进闭环）。

## 2. 推进原则

| 编号 | 原则 | 说明 | 反例 |
|---|---|---|---|
| P-01 | **先测量，后优化** | 任何性能/质量优化前必须先有基线数据，否则无法判断是否有效 | 「感觉快了」 |
| P-02 | **先加护栏，再拆房子** | 架构重构前必须先有测试与门禁；无护栏的重构一律拒绝 | 直接重写 `PlayerController` |
| P-03 | **小步快跑，每次可回滚** | 单个 PR 只做一件事，可独立回滚 | 一个 PR 同时拆文件 + 改逻辑 |
| P-04 | **契约先行** | 涉及接口/存储/平台能力的改动，先写方案与文档，再写代码 | 直接改 API 参数 |
| P-05 | **不留半成品** | 不允许「先注释掉」「先 TODO」「下个迭代再说」长期悬挂 | `// TODO: 后面处理` |
| P-06 | **纪律优先于速度** | 门禁不通过不合并；宁可延后，不可带病发布 | 跳过 analyze 提交 |

## 3. 里程碑总览

| 里程碑 | 名称 | 目标一句话 | 预计迭代 | 退出标志 | 对应版本 |
|---|---|---|---|---|---|
| **M0** | 基线固化 | 让「当前状态」可复现、可度量、可交接 | 2 | 基线文档 + 门禁脚本 + 台账就绪 | v2.2.x |
| **M1** | 质量地基 | 让每次改动都有自动化的正确性检查 | 3 | 覆盖率 ≥ 30%，analyze 零警告，CI 跑通 | v2.3.0 |
| **M2** | 架构解耦 | 消除巨型文件与隐式依赖 | 3 | 最大文件 ≤ 600 行，依赖规则有脚本门禁 | v2.4.0 |
| **M3** | 数据与缓存治理 | 统一四套存储，修复缓存缺陷 | 3 | 缓存抽象统一，TD-01/02/05/06/09 关闭 | v2.5.0 |
| **M4** | 播放内核加固 | 播放状态机化，错误可恢复、可观测 | 3 | 状态机落地，播放成功率可度量 | v2.6.0 |
| **M5** | 跨平台与发布 | 具备正式分发能力 | 2 | release 签名 + 多 ABI + 发布流程自动化 | v2.7.0 |
| **M6** | 体验与性能 | 启动、滚动、内存、包体积达标 | 2 | 各项性能基线达标 | v2.8.0 |
| **M7** | 工程可持续 | 流程闭环，可多人协作 | 2 | 贡献者流程 + 文档健康度 + 安全合规 | v3.0.0 |

**合计 20 个迭代**（按 2 周/迭代 ≈ 40 周）。

> ⚠️ **容量不匹配（必须在 I01 决策）**：WBS 实测需求 **135.5 人日**（68 个任务逐行求和），
> 而 20 个迭代按每迭代承诺 5 人日只能提供 **100 人日**，**缺口 35.5 人日 ≈ 7 个迭代**。
> 上表的「预计迭代」列因此是**乐观排期**。出路三选一见 `07-推进计划/迭代排期与节奏.md` §5.2，
> 风险登记见 `07-推进计划/风险登记册.md` **R-16**。

## 4. 里程碑依赖关系

```
M0 基线固化
 ├─▶ M1 质量地基
 │     └─▶ M2 架构解耦
 │           └─▶ M3 数据与缓存治理
 │                 └─▶ M4 播放内核加固
 │                       └─▶ M6 体验与性能
 ├─▶ M5 跨平台与发布（可与 M2/M3 并行，但依赖 M1 的门禁）
 └─▶ M7 工程可持续（依赖 M1–M5 的产出）
```

| 约束 | 说明 |
|---|---|
| M1 必须先于 M2 | 无测试保护的架构重构风险不可控 |
| M1 必须先于 M5 | 发布流程必须建立在自动化门禁之上 |
| M3 必须先于 M4 | 播放内核加固需要稳定的缓存层 |
| M7 最后 | 流程闭环需要前面所有里程碑的实际数据 |

## 5. 各里程碑风险与缓解

> **DoR / DoD / 交付物清单 / 对应版本 / 计划日期**不在本文重复——它们是 `07-推进计划/里程碑与版本路线图.md` §4 的职责，那里逐里程碑给出完整表格。
> 本文只保留总纲独有的**风险与缓解策略**（与 `07-推进计划/风险登记册.md` 的 `R-nn` 条目互补：这里是「按里程碑怎么防」，那里是「按风险怎么处置」）。

| 里程碑 | 主要风险 | 缓解策略 |
|---|---|---|
| **M0** 基线固化 | 文档工作量被低估 | 用「先骨架后填充」策略，允许 L1 契约先占位 |
| **M1** 质量地基 | 收紧 lint 会产生大量存量告警 | 分批开启，先只对新增代码 `warnings-as-errors` |
| **M2** 架构解耦 | 拆分引入回归 | 每个 PR 只拆一个文件，拆分前后功能对照测试 |
| **M3** 数据与缓存治理 | 目录迁移可能丢用户缓存 | 保留旧目录一次性搬移，失败回退 |
| **M4** 播放内核加固 | 状态机改动面大 | 保留旧路径开关，灰度验证 |
| **M5** 跨平台与发布 | 密钥管理不当 | 密钥不入库，使用 `key.properties` + 环境变量 |
| **M6** 体验与性能 | 优化无收益 | 每个优化点先测量、后改动、再测量 |
| **M7** 工程可持续 | 单人维护缺乏动力 | 用自动化替代人工巡检 |

## 约束与坑

| 编号 | 约束 | 说明 |
|---|---|---|
| G-01 | 里程碑顺序不可颠倒，但 M5 可与 M2/M3 并行 | 见 §4 依赖表 |
