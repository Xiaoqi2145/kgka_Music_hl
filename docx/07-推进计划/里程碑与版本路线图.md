# 里程碑与版本路线图

## TL;DR

1. 路线图把 `07-推进计划/工程化推进总纲.md`（KA-07-01）的 M0–M7 八个里程碑映射到 **20 个迭代（2 周/迭代，40 周）** 与 **8 个版本号**：M0→v2.2.x、M1→v2.3.0、M2→v2.4.0、M3→v2.5.0、M4→v2.6.0、M5→v2.7.0、M6→v2.8.0、M7→v3.0.0。
2. 起点版本是 **v2.2.0**（`pubspec.yaml:4`、`lib/config/app_config.dart:7`、`update.md:3`），但 Git 里已经存在 `v2.3.0`（2026-07-09）与 `v2.5.0`（2026-07-28）两个**与 `update.md` 无对应条目**的标签，本路线图的 M1/M3 目标版本与它们撞号——**必须在 M0 内先处置标签，否则版本历史不可信**（见 §6）。
3. 排期无缓冲：WBS 总量 125.5 人日 ÷ 20 迭代 = **6.3 人日/迭代**，已接近单人维护的满负荷上限（10 工作日 × 0.65 有效系数）；这是本路线图最大的进度风险（见 `07-推进计划/风险登记册.md` R-04）。

## 5. 版本号规则

| 规则 | 内容 | 依据 |
|---|---|---|
| 编号格式 | `主版本.次版本.补丁`（如 `2.3.0`） | `update.md` 既有写法 |
| 主版本 +1 | 破坏性变更：发布签名更换、存储 schema 不兼容迁移、公开 API 破坏 | M5 + M3 + M2 叠加 |
| 次版本 +1 | 里程碑级功能或工程能力交付（M1–M6 每个里程碑一次） | 本路线图 §2 |
| 补丁 +1 | 仅缺陷修复与工程基线，不含新功能（M0 用 v2.2.1） | — |
| `+build` 号 | **必须写**，且与 `AppConfig.appVersionCode` 相同（当前应为 `+220`）。不写会导致 APK `versionCode` 回落为 1 | `01-项目总览/构建与发布流程.md` §4.1 |
| 四落点同步 | `pubspec.yaml:4`、`lib/config/app_config.dart:7`、`:8`、`update.md:3` 必须同一次提交内一致 | TD-28、T-M0-03 |
| 标签规则 | 每个版本必须打同名标签（`git tag vX.Y.Z`），标签名与 `AppConfig.appVersion` 一致 | `01-项目总览/构建与发布流程.md` 步骤 12 |
| 版本号不再复用 | 已发布过的版本号不得回收重发（避免「同名不同包」） | 与 TD-28 配套 |

| 方案 | 动作 | 优点 | 缺点 | 建议 |
