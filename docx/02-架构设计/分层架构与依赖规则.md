# 分层架构与依赖规则

## TL;DR

项目采用**严格单向分层**：`config → core → models → services → controllers → ui`，`main.dart` 是唯一的装配点。经全量 import 扫描验证：`services` 不依赖 `controllers/ui`，`controllers` 不依赖 `ui`，`models` 与 `core` 无反向依赖。**这条规则是本项目最重要的架构约束，必须由评审守住**。

---

## 1. 分层定义

| 层 | 目录 | 文件数 | 职责 | 允许依赖 |
|---|---|---|---|---|
| 配置层 | `lib/config/` | 1 | 编译期常量、运行时覆盖、TTL/上限常量 | 仅 `shared_preferences` |
| 核心层 | `lib/core/` | 1 | HTTP 传输、重试、超时、session | `config`、`http` |
| 模型层 | `lib/models/` | 3 | 纯数据模型 + JSON 解析 | 仅 Dart 标准库 |
| 服务层 | `lib/services/` | 15 | 无 UI 依赖的业务能力 | `config`、`core`、`models` |
| 控制器层 | `lib/controllers/` | 5 | 状态持有与业务编排（`ChangeNotifier`） | `config`、`models`、`services` |
| UI 层 | `lib/ui/` | 35 | 页面、组件、主题、布局 | 全部下层 |
| 装配点 | `lib/main.dart` | 1 | 手动 DI、应用外壳 | 全部 |

---

## 2. 依赖方向（已核验）

### 2.1 规则

```
config  ←  core  ←  services  ←  controllers  ←  ui
              ↖  models  ↗
```

- **只允许向右（更高层）依赖，禁止反向**。
- `models` 可被任何层依赖，但它自身不依赖任何业务层。
- `main.dart` 例外：它是装配点，允许依赖所有层。

### 2.2 核验结果

| 检查项 | 命令 | 结果 |
|---|---|---|
| `services/` 是否 import `ui/` 或 `controllers/` | grep `^import '(\.\./|\./)(ui|controllers)/` in `lib/services` | ✅ 0 处 |
| `controllers/` 是否 import `ui/` | grep `^import '(\.\./|\./)(ui)/` in `lib/controllers` | ✅ 0 处 |
| `models/` 是否 import 业务层 | grep `^import '(\.\./|\./)(ui|controllers|services|core)/` in `lib/models` | ✅ 0 处 |
| `core/` 是否 import 业务层 | grep 同上 in `lib/core` | ✅ 0 处 |
| `ui/` 是否依赖 `controllers/services/models/config` | grep `^import '(\.\./)+(core|services|controllers|models|config)/` in `lib/ui` | ✅ 大量，符合预期 |

**结论**：分层纪律目前是干净的。任何 PR 若打破上述任一「0 处」，必须给出理由并在评审中单独讨论。

### 2.3 UI 层对各层的实际依赖分布

| UI 依赖目标 | 出现文件数（约） | 说明 |
|---|---|---|
| `controllers/player_controller.dart` | 15+ | 几乎所有播放相关页面 |
| `services/music_api.dart` | 12+ | 页面直接调接口（见下方「越层」说明） |
| `models/music_models.dart` | 11+ | 数据类型 |

| `services/cache_service.dart` | 4 | 首页、歌单详情、`app_shell` |
| `config/app_config.dart` | 5 | 版本号、缓存上限展示 |
| `controllers/download_controller.dart` | 3 | 下载状态展示 |
| `services/*_service.dart`（其余） | 各 1–2 | 音效、桌面歌词、统计、搜索历史 |

## 3. 关键例外与「越层」现状

| 编号 | 现象 | 位置 | 性质 | 处置建议 |
|---|---|---|---|---|
| A-01 | **UI 直接调用 `MusicApi`**，绕过控制器 | 首页、搜索、歌单详情、云盘、歌手页、评论页等 | 违反「UI 不直接触达数据源」的理想模型，但当前是**普遍且有意**的做法：这些页面是一次性数据展示，无需全局状态 | 保留，但规定：**涉及跨页面共享的状态必须放控制器**；纯展示型页面的直接调用需在文件头注释说明 |
| A-02 | `PlayerController` 反向持有 `DownloadController` 与 `CacheService` | `lib/controllers/player_controller.dart:107,110` | 控制器之间互相依赖（同层依赖） | 允许，但必须单向：`PlayerController → DownloadController`，禁止反向 |
| A-03 | `PlayerController` 直接实例化 5 个 Service | `lib/controllers/player_controller.dart:204-207,327` | 内部硬编码依赖，不利于测试替换 | 后续引入构造注入（见 WBS T-M2-05） |
| A-04 | UI 层 import `services/playback_stats_service.dart`、`desktop_lyrics_service.dart` 直接读服务 | 统计页、桌面歌词设置页 | 越层读取 | 收敛到控制器或只读视图模型 |
| A-05 | `main.dart` 承担了全局背景层与系统 UI 覆盖 | `lib/main.dart:158-290` | 装配点承载了 UI 职责 | 拆到 `lib/ui/` |

## 4. 装配规则（手动 DI）

```
main()
 ├─ AppConfig.loadCustomBaseUrl()          // 先恢复用户 API 地址
 ├─ ApiClient()                            // 唯一 HTTP 实例
 ├─ MusicApi(client)                       // 依赖注入
 ├─ AudioService.init(builder: MusicAudioHandler.new)
 ├─ ThemeController() + load()
 └─ runApp(KaMusicApp(...))

_KaMusicAppState.initState()
 ├─ CacheService()
 ├─ DownloadService()
 ├─ DownloadController(downloadService, api)
 ├─ AuthController(api, cacheService)
 ├─ LocalMusicController()
 ├─ PlayerController(api, audioHandler)
 │    ..downloadController = downloads      // 后置注入（循环依赖解法）
 │    ..cacheService = cacheService
 └─ ArtworkCacheService.instance.initialize()
```

| 规则 | 说明 |
|---|---|
| R-01 | 所有单例式依赖（`ApiClient`、`MusicApi`、`CacheService`、`DownloadService`、`AudioHandler`）**只在 `main.dart` 创建一次** |
| R-02 | 服务层**不持有状态**，可被安全复用 |
| R-03 | 控制器通过构造函数注入依赖；仅 `PlayerController` 因循环依赖使用后置字段注入 |
| R-04 | 新增全局依赖必须同时更新 `main.dart` 与本文件 |
| R-05 | 禁止在 UI 层 `new` 服务或控制器 |

---

## 5. 约束与坑

1. **无 DI 容器**：新增依赖需要手工改 `main.dart`，容易漏。
2. **`PlayerController` 是事实上的「上帝对象」**：2 833 行，持有音频、歌词、音效、会话、统计、下载六个关注点，任何一处改动都可能影响播放。
3. **UI 直接调 API 导致缓存策略分散**：部分页面用 `CacheService.swr`，部分直接请求，缓存命中率不可预测。
4. **`ArtworkCacheService` 是静态单例**（`ArtworkCacheService.instance`），与其他依赖的注入风格不一致。
5. **`AppConfig` 用静态可变字段存自定义 API 地址**（`_customBaseUrl`），全局可变状态，测试时需注意串扰。
6. **分层无编译期保障**：没有 `lint` 规则或包结构约束，只能靠评审。
