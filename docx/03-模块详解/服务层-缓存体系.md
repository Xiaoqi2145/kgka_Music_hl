# 服务层 · 缓存体系

## TL;DR

项目有**四套互不统一的本地存储**：数据缓存（接口 JSON，SWR + 分级 TTL）、缩略图缓存（封面图，LRU 按访问时间）、播放缓存（音频，LRU 按写入时间）、下载（用户主动，无上限）。四者各自实现、各自淘汰、各自统计，**没有统一的缓存抽象**；且播放缓存的 LRU 依据与缩略图缓存不同（写入时间 vs 访问时间），这是当前最容易出错的地方。

---

## 1. 四套存储总览

| 存储 | 实现 | 目录 | 目录 API | 载体 | 上限 | 淘汰依据 | 用户可清理 |
|---|---|---|---|---|---|---|---|
| 数据缓存 | `CacheService` | `data_cache/` | `getTemporaryDirectory()` | JSON 文件 + SharedPreferences 迁移 | 无上限（靠 TTL） | 无（仅 TTL 过期） | ✅ 设置页 |
| 缩略图缓存 | `ArtworkCacheService` | `ka_music_artwork/` | `getApplicationSupportDirectory()` | `.img` 二进制文件 | 512MB（64MB~4GB） | LRU，文件 `lastModified` | ✅ 设置页 |
| 播放缓存 | `DownloadController` + `DownloadService` | `ka_music_play_cache/` | `getTemporaryDirectory()` | 音频文件 | 300MB（100MB~10GB） | LRU，索引 `cachedAt` | ✅ 设置页 |
| 下载 | `DownloadController` + `DownloadService` | `ka_music_downloads/` | `getApplicationDocumentsDirectory()` | 音频文件 | 无上限 | 无（用户手动删） | ✅ 设置页 |

> ⚠️ **不一致点**：`AppConfig.cacheDirName = 'ka_music_cache'`（`lib/config/app_config.dart:26`）**定义了但从未被使用**——`CacheService` 硬编码 `'data_cache'`（`lib/services/cache_service.dart:32`）。已登记为技术债 TD-07。

## 2. 数据缓存（`CacheService`）

### 2.1 存储格式

每条缓存是一个文件，内容为：

```json
{ "savedAt": 1757300000000, "payload": { /* 任意 JSON */ } }
```

- 文件名 = `base64Url(utf8(key))` 去掉 `=` 填充 + `.json`（`cache_service.dart:43-44`）
- 写入走**临时文件 + 原子 rename**（`_writeRaw`，`cache_service.dart:109-114`）
- 编解码用 `compute()` 放到 isolate，避免卡 UI（`cache_service.dart:83,102`）

### 2.2 key 命名规范（`cache_service.dart:47-61`）

| key 模式 | 内容 | 登出时清理 |
|---|---|---|
| `cache_home` | 首页推荐（匿名可访问） | ❌ 保留 |
| `cache_playlist_{playlistId}` | 歌单详情 | ✅ |
| `cache_album_{albumId}` | 专辑详情 | ✅ |
| `cache_artist_{artistId}` | 歌手详情 | ✅ |
| `cache_user_{userId}` | 用户信息 | ✅ |
| `cache_user_playlists_{userId}` | 用户歌单列表 | ✅ |
| `cache_playback_session` | 播放会话（队列 + 当前曲 + 模式） | ❌ 保留（TTL 3650 天） |

> 实际调用点：`home_page.dart:96,122,132`、`playlist_detail_page.dart:307-308,429-430`、`auth_controller.dart:528,531`、`player_controller.dart:248,1355`。

### 2.3 TTL 分级（`lib/config/app_config.dart:33-35`）

| 类型 | 常量 | 默认 TTL |
|---|---|---|
| 首页推荐 | `homeCacheTtl` | 30 分钟 |
| 歌单/专辑详情 | `playlistDetailTtl` | 24 小时 |
| 用户信息 + 歌单列表 | `userProfileTtl` | 24 小时 |
| `read()` 的默认值 | 参数默认 | 24 小时 |
| 播放会话 | 调用处显式 | 3650 天（≈永不过期） |

### 2.4 SWR 语义（`cache_service.dart:208-247`）

| 步骤 | 行为 |
|---|---|
| 1 | 非强制刷新：先 `read` → 命中则**立即** `onData(cached)`（不区分是否过期） |
| 2 | 强制刷新（下拉刷新）：仍然 `read`，但**不**立即回调，只作兜底 |
| 3 | 后台 `fetch()` → 成功则 `write` + `onData(fresh)` |
| 4 | `fetch` 失败且有缓存 → 降级，不报错；强制刷新模式下补一次 `onData(cached)` |
| 5 | `fetch` 失败且无缓存 → `onError` |

> **注意**：`isStale` 只被计算并返回，SWR 流程**不根据 `isStale` 做任何分支**——过期数据照样先显示。`isStale` 目前只有调用方自行判断的潜在用途。

### 2.5 读取时的 SharedPreferences 迁移

`read()` 若文件不存在，会回退读 `SharedPreferences` 中的旧数据，**成功读取后写文件并删除 prefs 键**（`cache_service.dart:74-79`）。这是一次性迁移逻辑，迁移完成后不再走该分支。

### 2.6 清理与统计

| 方法 | 行为 |
|---|---|
| `remove(key)` | 删文件 + 删 prefs 键 |
| `clearUserCache(userId)` | 按 4 个前缀删 prefs 键；再遍历目录，base64 反解文件名匹配前缀后删文件（`cache_service.dart:125-148`） |
| `clearAllCache()` | 递归删除 `data_cache` 目录 + 删除所有 `cache_` 开头的 prefs 键 |
| `getCacheSize()` | 目录文件字节数 + prefs 中 `cache_`/`ka_music_cached_playlists` 键的 `length * 2`（UTF-16 估算） |
| `getCacheCount()` | `.json` 文件数 + `cache_` 开头 prefs 键数 |

### 2.7 已知缺陷

| 编号 | 问题 | 位置 | 影响 |
|---|---|---|---|
| C-01 | `getCacheSize` 对 prefs 用 `length * 2` 估算，与实际不符 | `cache_service.dart:166` | 设置页显示值偏差 |
| C-02 | 数据缓存放在 `getTemporaryDirectory()`，**系统可随时清理**，与「离线可用」目标矛盾 | `cache_service.dart:35` | 系统清缓存后离线数据丢失 |
| C-03 | 无容量上限、无 LRU，只有 TTL；过期文件不会主动删除，只在下次 `read` 时被覆盖 | `CacheService` 全类 | 目录可无限增长 |
| C-04 | `clearAllCache` 保留 `ka_music_cached_playlists` 键，但 `getCacheSize` 又统计它 | `cache_service.dart:154-171,186-196` | 统计与清理口径不一致 |
| C-05 | `clearUserCache` 的 base64 反解在文件名非法时静默跳过（`catch (_) {}`） | `cache_service.dart:146` | 可能漏删 |

## 3. 缩略图缓存（`ArtworkCacheService`）

### 3.1 关键参数

| 项 | 值 | 位置 |
|---|---|---|
| 单例 | `ArtworkCacheService.instance` | `artwork_cache_service.dart:36` |
| 目录 | `getApplicationSupportDirectory()/ka_music_artwork` | `artwork_cache_service.dart:55-56` |
| 文件名 | `base64Url(utf8(url))` 去 `=` + `.img` | `artwork_cache_service.dart:64-65` |
| 默认上限 | `AppConfig.defaultArtworkCacheMaxBytes` = 512MB | `app_config.dart:42` |
| 可调范围 | 64MB ~ 4GB | `app_config.dart:43-44` |
| 持久化键 | `settings.artwork_cache_max_bytes` | `artwork_cache_service.dart:38` |
| 淘汰依据 | 文件 `lastModified`（命中时刷新） | `_touch`，`artwork_cache_service.dart:141-147` |

### 3.2 读取链路

```
CachedArtworkImage (ImageProvider)
  └─ ArtworkCacheService.load(url)
       ├─ _pending 中已有同 URL → 复用同一个 Future（合并并发请求）
       ├─ 磁盘命中（存在且 length>0）→ 异步 _touch 刷新访问时间 → 返回 File
       └─ 未命中 → _download()
            ├─ HttpClient，connectionTimeout 8s，响应 12s 超时
            ├─ 重定向最多 3 次
            ├─ 写 .part → 校验非空 → 删除旧文件 → rename 原子替换
            └─ 失败 → 删除 .part，返回 null（界面降级为占位图）
```

### 3.3 淘汰算法（纯函数，可测）

`selectLruEvictions(entries, maxBytes)`（`artwork_cache_service.dart:257-280`）：

1. 求和；若 `total <= maxBytes` 返回空列表。
2. 按 `accessedAt` 升序排序，**时间相同则按 `path` 字典序**（保证稳定）。
3. 从最旧开始累加删除，直到剩余 ≤ 上限。

`_pruneToLimit()` 循环调用 `_prune()` 直到 `_totalBytes <= maxCacheBytes` 或无法继续删除（防死循环，`artwork_cache_service.dart:207-214`）。

### 3.4 并发与计数

| 机制 | 实现 |
|---|---|
| 在途请求合并 | `_pending: Map<String, Future<File?>>`，`whenComplete` 中移除 |
| 加载状态去重 | `_loading` Future，`_loaded` 标志 |
| 淘汰去重 | `_pruning` Future，同一时刻只跑一次 `_pruneToLimit` |
| 计数 | `_totalBytes` / `_entryCount` 内存维护，命中/新增时增减 |

### 3.5 已知缺陷

| 编号 | 问题 | 位置 | 影响 |
|---|---|---|---|
| C-06 | **`_prune` 用扫描快照覆盖内存计数**（`_totalBytes = total - removedBytes`），扫描期间并发下载的增量被丢弃 | `artwork_cache_service.dart:250-251` | 计数偏小 → 上限可能被突破 |
| C-07 | **淘汰只到硬上限、无低水位**：达到上限后每次新增都触发全目录扫描（每文件 2 次 syscall） | `_enforceLimit` | 万级文件时卡顿 |
| C-08 | `.part` 残留文件**不计入大小/条目，启动时也不清理** | `_loadState` 只统计 `.img` | 磁盘泄漏 |
| C-09 | **无失败缓存**：断网时每个未缓存封面都会重试一次 8s 连接超时 | `_download` | 弱网下大量超时 |
| C-10 | 有意不缓存的封面（首页大卡、FM 头图、歌手头图）仍走 `Image.network` | `KA-Music-项目状态.md` | 离线时这些位置无图（设计取舍） |

## 4. 播放缓存（`DownloadController` + `DownloadService`）

### 4.1 参数

| 项 | 值 | 位置 |
|---|---|---|
| 目录 | `getTemporaryDirectory()/ka_music_play_cache` | `download_service.dart:62-68` |
| 文件名 | `{sanitizedHash}_{quality.apiValue}.{mp3|flac}` | `download_service.dart:72-76` |
| cacheKey | `{sanitizedHash}_{quality.apiValue}` | `download_service.dart:79-82` |
| 默认上限 | 300MB | `app_config.dart:38` |
| 可调范围 | 100MB ~ 10GB | `app_config.dart:39-40` |
| 持久化键 | `settings.play_cache_max_bytes` | `download_controller.dart` |
| 索引持久化键 | `ka_music_play_cache_index` | `download_controller.dart` |
| 淘汰依据 | 索引中的 `cachedAt`（**写入时间，非访问时间**） | `_prunePlayCache`，`download_controller.dart:518-545` |

### 4.2 触发时机

`PlayerController._schedulePlaybackCache()`（`player_controller.dart:1010+`）：切歌后**连续稳定播放 30 秒**才发起缓存，避免快速切歌产生无效网络与磁盘 IO。

### 4.3 优先级（`localSourceFor`，`download_controller.dart:264-282`）

```
已下载（且音质一致） > 播放缓存（同音质） > null（走网络）
```

### 4.4 已知缺陷

| 编号 | 问题 | 影响 |
|---|---|---|
| C-11 | 淘汰依据是 `cachedAt` 而非访问时间，**热门老歌可能被冷门新歌挤掉** | 命中率下降 |
| C-12 | 播放缓存放在 `getTemporaryDirectory()`，系统可清理 | 离线播放不可靠 |
| C-13 | 用户下载与播放缓存共享并发上限（3），但下载优先 | 播放缓存可能长期排队 |
| C-14 | 音质变化导致同曲不同 key，可能同时缓存多档 | 空间浪费 |

## 5. 约束与坑（跨缓存共性）

| 编号 | 约束 | 影响 |
|---|---|---|
| CB-01 | 三套缓存各自实现淘汰，**没有统一接口**，设置页需分别统计 | 新增缓存类型成本高 |
| CB-02 | 缩略图按访问时间淘汰、播放缓存按写入时间淘汰，**语义不一致** | 用户与开发者都难以预测行为 |
| CB-03 | 数据缓存与播放缓存位于临时目录，系统可清理 | 离线能力不可靠 |
| CB-04 | 无统一容量上限与低水位，淘汰触发时机不可预测 | 卡顿风险 |
| CB-05 | 缓存异常一律静默降级，无日志、无失败统计 | 线上问题不可见 |
| CB-06 | 缓存键依赖 URL / hash 的规范化，规范化不一致会产生重复条目 | 空间浪费 |

## 6. 统一治理建议（对应 WBS T-M3-01）

| 目标 | 措施 |
|---|---|
| 统一抽象 | 抽出 `DiskCache` 接口（`get/put/evict/clear/size`），三套缓存复用 |
| 统一 LRU 依据 | 全部改为「访问时间」，或明确文档化差异并接受 |
| 统一目录策略 | 需要离线可用的（缩略图、播放缓存、数据缓存）放 `ApplicationSupportDirectory`；纯临时数据放 temp |
| 引入低水位 | 淘汰到 `0.8 × 上限`，避免每次新增都全目录扫描 |
| 失败缓存 | 记录失败 URL + 时间戳，短期不再重试 |
| 统一统计口径 | 设置页数值全部来自同一套 API |
