## 一句话结论（TL;DR）

1. 技术方案必须**先给可选方案与取舍表，再给选定方案**；没有对比的方案不予评审（`../07-推进计划/工程化推进总纲.md` P-04 契约先行）。
2. 「目标」必须可验收（数值或可执行动作），「非目标」必须显式写出——本项目最常见的失败是范围蔓延（一个 PR 同时拆文件 + 改逻辑 + 调 UI）。
3. 示例方案为 **`T-M2-01` 拆分 `player_page.dart`**：现状 3290 行（文件真实 3536 行）、9 个可拆分单元、估算 4.0 人日、验收「最大文件 ≤ 600 行 + 功能对照录屏一致」。

## 1. 背景与问题

- `lib/ui/pages/player_page.dart` 是项目最大文件：3290 行（`Measure-Object -Line` 口径），文件真实行数 3536；台账 `TD-10` 记为 3537 行。

- M2 退出标准要求「最大单文件 ≤ 600 行」（`../07-推进计划/工程化推进总纲.md` §5），本方案是达成该标准的第一刀。

| 非目标 | 不修改 `PlayerController` 的公开 API 与内部结构 | 另立方案（`T-M2-02`） |
| 非目标 | 不统一其余 3 份歌曲行组件 | 另立任务 |

## 6. 详细设计

| 子节 | 内容 |
|---|---|
| 数据流 | 拆分后不变：`PlayerPage` → `_PlayerBody`（竖/横屏分叉）→ `PlayerPosterPage` / `PlayerLyricsPage` / `PlayerLandscape` → `PlayerControls`；歌词侧 `LyricViewport` → `KaraokeLine`。控制器仍由 `PlayerPage` 接收后逐层构造注入，不新增单例 |
| 接口 | `PlayerPage` 构造签名**不变**；内部类跨文件后由 `_Xxx` 改为公开 `Xxx`（如 `LyricViewport`），这是唯一的可见性变化，需在 PR 中逐项列出 |
| 状态与生命周期 | 当前页索引、横竖屏判定留在 `_PlayerBodyState`；歌词滚动偏移/对齐随 `_LyricViewportState` 原样迁移；背景解码随 `_ArtworkBackgroundState` 原样迁移；方向强制/恢复（`:52-56` 进入放开、`:66-78` 退出恢复）留在 `_PlayerPageState` 不动 |
| 错误处理 | **不新增任何错误处理分支**（新增分支属行为变更，违反非目标）；背景解码失败仍回退 `_FallbackBackground`，歌词为空仍走现有占位/错误文案；拆分遗漏引用由编译期报错拦截 |
