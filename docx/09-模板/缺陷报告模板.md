## 一句话结论（TL;DR）

1. 缺陷编号固定为 `KA-BUG-YYYYMMDD-nn`（`nn` 为当日两位序号），严重级固定 `P0~P3` 四级，**标题必须一句话说清「什么条件 → 什么现象 → 什么后果」**。
2. 报告必须能**脱离报告人独立复现**：环境、步骤、期望、实际、日志四要素缺一不可；根因分析必须给出 `文件:行号` 锚点，否则只能标「待核实」。
3. **现状没有缺陷报告模板**（`docx/08-工程纪律/缺陷处理纪律.md` 尚未生成，待核实）；台账已登记 38 条技术债/缺陷，本模板的填写方式与台账字段保持一致。

## 3. 逐字段填写规则

### 3.1 编号与标题

| 字段 | 规则 | 正例 | 反例 |
|---|---|---|---|
| 编号 | `KA-BUG-` + 报告日期（8 位）+ `-` + 当日两位序号 | `KA-BUG-20260909-01` | `BUG1`、`bug缓存` |
| 标题结构 | 「条件 + 现象 + 后果」 | 缩略图缓存并发下载时计数偏小，导致磁盘占用突破 512MB 上限 | 缓存有 bug |
| 标题长度 | ≤ 40 字 | — | 一长段复现步骤 |
| 与台账关系 | 若台账已有同问题条目（`TD-xx`），**标题沿用台账措辞**并填写「关联编号」 | — | 同一问题开两张单 |

### 3.2 严重级定义

| 级别 | 判定标准 | 典型例子 | 处置时限（建议） |
|---|---|---|---|
| P0 | 崩溃 / 数据丢失 / 登录不可用 / 无法启动 | 启动即闪退；登录态丢失 | 立即 |
| P1 | 核心功能不可用或产生不可逆后果（存储失控、播放中断、覆盖用户数据） | `TD-01` 缓存上限被突破；`TD-02` 系统清缓存导致离线内容消失 | 当前迭代 |
| P2 | 功能可用但明显错误、体验受损，有绕过办法 | 歌词错位、排序失效、页面穿透 | 下个迭代 |
| P3 | 轻微、外观、文案、极端边界 | 文案错别字、极小概率布局错位 | 排期处理 |

> 与台账口径一致：台账 38 条中 P0 = 0、P1 = 4、P2 = 14、P3 = 20。

### 3.3 复现概率

| 取值 | 判定标准 | 记录要求 |
|---|---|---|
| 必现 | 每次按步骤都出现 | 给出确定性步骤 |
| 高频 | > 50% | 给出「N 次中 M 次」 |
| 偶发 | < 50% | 说明并发/时序/网络条件猜测 |
| 仅一次 | 无法再复现 | 必须附完整日志，否则标记「无法复现」 |

### 3.4 环境字段（缺一项即视为不完整）

| 字段 | 取值来源 | 为什么必须 |
|---|---|---|
| 应用版本 | 关于页 / `AppConfig.appVersion`（`lib/config/app_config.dart:7`） | 版本间行为差异大（如 v2.2.0 修复登录页 API 地址） |
| 平台 | `defaultTargetPlatform` | 除 Android 外大量能力为「不支持/未验证」（见 `../05-平台与原生/多平台差异矩阵.md`） |
| 系统版本 | 系统设置 | 分区存储、通知权限、前台服务行为随版本变化 |
| 设备型号 | 系统设置 | 大屏/平板与手机布局分支不同（`AdaptiveLayout.isTabletByPlatform()`） |
| 网络 | 实测 | 弱网/断网会触发降级与重试路径 |
| 关键设置 | 设置页 | 缓存上限、音质、智能音质、主题等直接改变行为 |
| 数据前置 | 实测 | 缓存条数、下载任务数影响淘汰与并发路径 |

### 3.5 根因分析要求

| 要求 | 说明 |
|---|---|
| 必须有锚点 | `文件路径:行号`（如 `lib/services/artwork_cache_service.dart:250-251`）或 `文件路径:类名.方法名` |
| 必须区分「现象」与「根因」 | 「计数偏小」是现象，「扫描快照覆盖内存计数」是根因 |
| 无法定位时 | 写「待核实」并列出已排除项与下一步验证动作，不得编造 |
| 已有台账条目时 | 直接引用 `TD-xx`，不重复描述 |

### 3.6 关闭结论

| 结论 | 附加要求 |
|---|---|
| 已修复 | 必须填修复版本 + 回归验证结论 + 台账状态更新 |
| 不修复 | 必须写清理由与影响范围，并转登记为技术债（`TD-xx`） |
| 无法复现 | 保留报告，标注「无法复现」，附当时的日志；同类反馈累计 2 次以上必须重启调查 |
| 转技术债 | 在台账新建或复用条目，并在本文填写编号 |

## 4. 完整填写示例

> **示例说明**：本示例的技术事实（根因、锚点、影响、建议修复、验收方式）全部取自 `../06-质量保障/已知问题与技术债台账.md` 的 `TD-01`；**环境与观测数值为填写格式示例**，不代表一次真实用户报告。

```markdown
## 基本信息

| 项 | 内容 |
|---|---|
| 编号 | KA-BUG-20260909-01 |
| 标题 | 缩略图缓存扫描期间并发下载时计数偏小，导致磁盘占用突破 512MB 上限 |
| 严重级 | P1 |
| 复现概率 | 偶发（<50%，需并发下载与淘汰同时发生） |
| 首次出现版本 | 待核实（`artwork_cache_service.dart` 引入 LRU 淘汰与可配置上限的版本，即 v2.2.0 相关提交） |
| 报告人 / 日期 | 示例 / 2026-09-09 |
| 关联编号 | TD-01、T-M3-02、G-02、RC-CA-01 |

## 环境

| 项 | 值 |
|---|---|
| 应用版本 | v2.2.0（`AppConfig.appVersion` = '2.2.0'） |
| 平台 | Android |
| 系统版本 | Android 14（示例） |
| 设备型号 | 示例机型（arm64-v8a） |
| 网络 | WiFi（示例） |
| 关键设置 | 缩略图缓存上限 = 512MB（默认，`AppConfig.defaultArtworkCacheMaxBytes`） |
| 数据前置 | 已浏览大量封面，缓存条目数千级；同时触发多张封面下载 |

## 复现步骤

1. 进入设置 → 缓存管理，确认「缩略图缓存」上限为默认 512MB。
2. 连续快速浏览首页、歌单详情、歌手详情等含封面的列表，使 `ka_music_artwork` 目录接近上限。
3. 在缓存接近上限时，让多个封面同时开始下载（快速来回切换列表页）。
4. 观察设置页显示的缩略图缓存占用大小与设备上该目录的实际大小。

**前置条件**：缓存总量必须已接近上限，且第 3 步的下载要与后台的 `_prune` 扫描发生重叠。

## 期望行为

设置页显示的占用大小与实际目录占用一致；无论并发如何，占用都不应超过用户设定的上限（默认 512MB）。

## 实际行为

设置页显示的占用大小偏小（低于实际目录占用），且实际目录占用可以超过上限。示例观测：显示 498MB、实际 531MB。

| 项 | 内容 |
|---|---|
| 首次出现 | 待核实 |
| 最后正常 | 不适用（该策略为后引入） |
| 定位方式 | 代码阅读 + 单测复现 |

## 根因分析

| 项 | 内容 |
|---|---|
| 根因 | `_prune` 用「扫描开始时的目录快照」覆盖内存计数，扫描期间并发下载累加的增量被丢弃 |
| 证据（锚点） | `lib/services/artwork_cache_service.dart:250-251` |
| 关键代码 | `_totalBytes = total - removedBytes;` / `_entryCount = entries.length - removedCount;`（`total` 为扫描开始时的目录总和） |
| 触发条件 | 目录扫描（启动一次 + 每次新增缓存后）与封面下载并发 |
| 影响面 | 计数偏小 → 上限可被突破 → 磁盘占用不受控；仅影响缩略图缓存，不影响播放与下载 |
| 是否已有台账条目 | 有，`TD-01`（P1，未修复，关联任务 `T-M3-02`） |

## 修复方案

| 项 | 内容 |
|---|---|
| 方案 | 改为「按删除量扣减」：`_totalBytes -= removedBytes`；`_entryCount -= removedCount` |
| 备选方案 | 维护内存索引（path → size）作为唯一真相；取舍：实现更重，但可同时解决 `TD-09`（`.part` 残留不计入） |
| 改动点 | `lib/services/artwork_cache_service.dart:250-251` |
| 风险 | 若删除过程中有文件被并发删除，扣减会偏大；需在删除失败时回退扣减 |
| 关联任务 | `T-M3-02` |

## 回归验证

| 项 | 内容 |
|---|---|
| 验证方式 | 自动化：模拟扫描期间新增文件，断言 `_totalBytes` 与目录实际总和不漂移；手工：RC-CA-01、RC-CA-06 |
| 新增用例 | 建议新增到 `test/artwork_cache_lru_test.dart`（当前 7 例，仅覆盖 `selectLruEvictions` 纯函数） |
| 回归用例编号 | RC-CA-01（缓存大小显示）、RC-CA-06（离线显示已缓存封面） |
| 验证结论 | 未验证（`TD-01` 状态为「未修复」） |
| 验证人 / 日期 | — |

## 关闭结论

| 项 | 内容 |
|---|---|
| 状态 | 未关闭（`TD-01` 当前为「未修复」） |
| 修复版本 | — |
| 台账状态更新 | 修复后把 `TD-01` 状态改为「已修复」 |
| 遗留 | `TD-05`（淘汰无低水位，达上限后每次新增触发全目录扫描）、`TD-09`（`.part` 残留不清理）为同类风险，需一并评估 |

## 5. 约束与坑

| # | 约束/坑 | 影响 | 核对锚点 |
|---|---|---|---|
| 1 | **没有崩溃上报**（`TD-04`），线上缺陷拿不到堆栈；报告里的「日志」必须靠用户导出或开发机 `adb logcat` 复现。 | 根因分析易停留在猜测 | `../06-质量保障/已知问题与技术债台账.md` TD-04 |
| 2 | 大量 `unawaited` 异常被 `catch (_) {}` 吞掉（`TD-25`），缺陷可能**静默发生且无日志**；此时必须在报告中写「无日志」，而不是省略该节。 | 无法定位 | 台账 TD-25 |
| 3 | 缓存类缺陷要看**两个口径**：设置页显示值 与 目录实际值。两者不一致本身就是缺陷证据。 | 误判为「已修复」 | `../03-模块详解/服务层-缓存体系.md` |
| 4 | 缩略图缓存位于 `getApplicationSupportDirectory()`，而数据缓存/播放缓存位于 `getTemporaryDirectory()`；系统「清除缓存」会清空后者。写环境时须注明是否清理过缓存。 | 复现结果不一致 | `TD-02` |
| 5 | 平台相关缺陷不得写成「全平台」；除 Android 外默认「未验证」，Web 的缓存/下载/本地音乐为「不支持」。 | 误导 | `../05-平台与原生/多平台差异矩阵.md` §2 |
| 6 | 同一问题不得重复开单：先在台账 §2 检索 `TD-xx`，命中则复用编号并补充复现信息。 | 台账膨胀 | 台账 §1 |
| 7 | 「修复方案」不得写「已修复」——修复状态由「回归验证」与「关闭结论」两节共同确认。 | 状态失真 | §3.6 |
| 8 | 缺陷修复后必须补/关联回归用例（`RC-xx`），否则视为未完成。 | 回归缺失 | `../06-质量保障/回归测试用例库.md` §0 |
