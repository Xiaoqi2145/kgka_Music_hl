# 版本历史与功能演进

## TL;DR

从 v1.0.0（首个发布）到 v2.2.0（当前）共 10 个记录版本，功能从「能播」演进到「播放 + 音效 + 歌词 + 下载缓存 + 本地音乐 + 个性化」的完整形态；**代码提交 125 次，但 `update.md` 只记录了 10 个版本，且 Git 标签 v2.3.0 / v2.5.0 在 `update.md` 中无对应条目**——版本记录与代码历史已出现脱节。

---

## 3. 版本号与 Git 标签对齐情况

| 项 | 现状 |
|---|---|
| `pubspec.yaml` version | `2.2.0` |
| `AppConfig.appVersion` | `2.2.0` |
| `AppConfig.appVersionCode` | `220` |
| APK 系统 versionCode | **1**（缺 `+220` 后缀导致，见 TD-39） |
| Git 标签 | 存在 `v2.3.0`（2026-07-09）、`v2.5.0`（2026-07-28） |
| `update.md` 条目 | 最新为 v2.2.0，**无 v2.3.0 / v2.5.0** |
| README 徽章 | 仍写 `Version 2.0.5` |

**结论**：版本元数据在 4 处各自漂移，**发布前必须逐项核对**（见 `09-模板/发布检查清单.md`）。

## 4. 演进趋势观察（供路线图参考）

| 观察 | 证据 | 对路线图的含义 |
|---|---|---|
| 功能增速快于工程质量投入 | 10 个版本带来 6.1 万行代码，但测试仅 1 239 行 | M1 质量地基必须先做 |
| 后期版本以「修复 + 体验」为主 | v2.0.5 起每版修复项 ≥ 5 条 | 技术债已开始反噬，需 M3/M4 治理 |
| 缓存/下载能力集中出现在 v2.0 之后 | 3 个缓存服务全部在 v2.0+ 引入 | 缓存治理（M3）优先级合理 |
| 平台扩展落后于功能 | 6 个平台目录存在，仅 Android 可用 | M5 需先明确平台取舍 |
| 文档记录滞后于代码 | 8 项能力未进 `update.md` | 建立「发布即更新」纪律 |
