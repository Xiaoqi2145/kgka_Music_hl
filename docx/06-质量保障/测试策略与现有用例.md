### 2.1 `test/artwork_cache_lru_test.dart` — LRU 淘汰纯函数

- **被测对象**：`ArtworkCacheService.selectLruEvictions(List<ArtworkCacheEntry> entries, int maxBytes)`，静态纯函数（`lib/services/artwork_cache_service.dart:257-280`）。
- **输入模型**：`ArtworkCacheEntry({required String path, required int size, required DateTime accessedAt})`（`artwork_cache_service.dart:11-23`）。
- **淘汰算法要点**：总量 `<= maxBytes` 时直接返回空（`:265`）；否则按 `accessedAt` 升序、**时间相同再按 `path` 升序**（`:267-271`），逐个扣减直到不超上限（`:274-278`）。

| # | 用例名 | 断言意图 |
|---|---|---|
| 1 | 总量未超过上限时不淘汰任何条目 | 200 < 1000 → `isEmpty` |
| 2 | 总量恰好等于上限时不淘汰 | 200 == 200 → `isEmpty`（边界：相等不淘汰） |
| 3 | 超出上限时淘汰最久未访问的条目 | 300 > 200 → 仅 `['old']` |
| 4 | 需要淘汰多条时按访问时间升序返回 | 300 > 100 → `['old','mid']`（**顺序敏感**） |
| 5 | 单个条目超过上限时同样被淘汰 | 单条 500 > 100 → `['huge']` |
| 6 | 访问时间相同时按路径稳定排序 | 时间相同 → 按 path 升序，返回 `['a']` |
| 7 | 空列表不抛异常 | `selectLruEvictions(const [], 0)` → `isEmpty` |

- **覆盖的边界**：空输入、总量等于上限、单条超限、淘汰多条、时间并列。
- **未覆盖的关键路径**：`_prune()` 的目录扫描与真实删除（`:216-252`）、`_enforceLimit()` 的并发合并（`_pruning`，`:193-205`）、`_pruneToLimit()` 的循环与死循环保护（`:207-214`）、`_touch()` 刷新访问时间（`:141-147`）、`clearCache()`（`:172-191`）、`setMaxCacheBytes()` 的取值钳位（`:162-169`）。

| 2 | no song is idle even while a load intent is resolving | 无曲目恒为 `idle` |
| 3 | loading outranks seeking and buffering | `loading` 高于 `seeking` / `buffering` |
| 4 | seeking outranks stalled and buffering | `seeking` 高于 `stalled` / `buffering` |
| 5 | buffering outranks stalled: a slow network is not an anomaly | `buffering` 高于 `stalled` |
| 6 | stalled only applies while playing | `stalled` 仅在播放中成立 |
| 7 | buffering outranks playing and paused | `buffering` 高于 `playing` / `paused` |
| 8 | the happy path is playing and a ready idle player is paused | 正常播放 → `playing`；ready 但未播 → `paused` |
| 9 | every phase is reachable | 枚举每一阶段都有可达输入（防死枚举） |
| 10 | every failure class has a recovery action | 每个失败类都有对应恢复动作 |
| 11 | every failure class has a user-visible message | 每个失败类都有用户可见文案 |
| 12 | empty URLs degrade quality while device loss never auto-resumes | 空 URL 走降级；设备丢失不自动恢复 |

## 3. 测试分层策略

| 层 | 目标 | 工具/手段 | 现有数量 | 何时必须写 | 现状评价 |
|---|---|---|---|---|---|
| **L1 纯函数单测** | 无 I/O、无平台依赖的算法与解析器 | `flutter_test` + 直接调用 | **37**（LRU 7 + 歌词解析 16 + 播放阶段/失败分类 13 + `artworkDecodePixels` 1） | 新增/修改纯函数、解析器、计算公式时**必写** | ✅ 覆盖最好，是本项目测试的样板 |

| **L3 服务层单测（含通道/文件系统）** | MethodChannel、文件系统、prefs | mock 通道 + 临时目录 + `HttpServer` | **18**（音量均衡 8 + 封面缓存 3 + 数据缓存 5 + 下载缓存 2） | 新增通道方法、缓存读写路径时**必写** | ⚠️ 只覆盖了 4 个服务，其余服务为 0 |

| **L5 Widget 测试** | 组件渲染、交互、状态刷新 | `testWidgets` + `pumpWidget` | **3**（`artwork_and_selector_test.dart`：`ListenableSelector` 2 + `Artwork` 1） | 新增/修改页面级交互时建议写 | ⚠️ 已从 0 起步，但只覆盖 2 个组件，**页面级交互仍为 0** |

**分层判定口径**：优先写成本最低、稳定性最高的层——同一个行为若能在 L1 验证，就不要写到 L4；只有当行为由「多个组件协作 + 时序」决定时才上升到 L4/L5。

**当前分布形状**：L1 37 + L2 40 + L3 18 + L4 42 + L5 3 = **140**，与 `flutter test` 实测总数一致。**逻辑层（L1–L4）占 137/140 = 97.9%**；L5 刚起步（3 例，仅组件级），L6 为 0，意味着**几乎没有任何一层能验证「用户看得见的完整流程」**。这是当前测试体系最明确的形状特征——不是覆盖率低，而是**覆盖面停在 UI 边界之外**。
