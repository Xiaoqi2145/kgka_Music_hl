## 3. 重点条目详情

### TD-01 缩略图缓存计数被扫描快照覆盖（P1）

**证据**：`artwork_cache_service.dart:250-251`

```dart
// 以本次扫描结果为准修正计数，避免与并发写入产生漂移。
_totalBytes = total - removedBytes;
_entryCount = entries.length - removedCount;
```

**问题**：`total` 是扫描**开始**时的目录总和。扫描期间 `_loadTracked` 可能已 `_totalBytes += downloaded.length()`，但随后被这行覆盖掉，导致计数偏小 → 上限可被突破。

**建议**：改为「按删除量扣减」（`_totalBytes -= removedBytes`），或维护内存索引（path → size）作为唯一真相。

**验收**：新增单测：模拟扫描期间新增文件，断言 `_totalBytes` 与目录实际总和不漂移。

### TD-02 缓存位于临时目录（P1）

**证据**：`cache_service.dart:35`（`getTemporaryDirectory()`）、`download_service.dart:63`（同）

**问题**：Android 系统「清除缓存」会清空 `getTemporaryDirectory()`，与「离线可播放 / 离线可显示」目标直接冲突。缩略图缓存已正确使用 `getApplicationSupportDirectory()`，两者不一致。

**建议**：数据缓存与播放缓存迁到 `getApplicationSupportDirectory()`，并做一次性迁移（旧目录存在则搬移）。

**验收**：手动清除系统缓存后，已缓存封面与已缓存音频仍可用。

### TD-03 release 使用 debug 签名（P1）

**证据**：`android/app/build.gradle.kts` → `signingConfig = signingConfigs.getByName("debug")`

**问题**：无法上架、无法覆盖安装升级、签名指纹不可控。

**建议**：引入 `key.properties`（不入库）+ `signingConfigs.release`；`buildKey.keystore` 从仓库移除并轮换密钥。

**验收**：`flutter build apk --release` 产物用 `apksigner verify --print-certs` 显示 release 证书。

### TD-04 无 CI 与崩溃上报（P1）

**问题**：125 次提交全部靠本地验证；`unawaited` 的异常被 `catch (_) {}` 吞掉，线上问题不可见。

**建议**：先落地本地门禁脚本（`flutter analyze` + `dart format --set-exit-if-changed` + `flutter test`），再接入 CI；错误上报可先用本地日志文件 + 用户导出。

**验收**：见 `08-工程纪律/测试与质量门禁.md` 的门禁命令全部可通过。

### TD-15 背景图渲染延迟（P2）

**证据**：`KA-Music-项目状态.md` §4.2

**现状**：用户反馈页面切换时背景图延迟约 0.7s。已尝试预加载字节、预解码 `ui.Image`、架构分离，均回退。当前 `main.dart` 用 `ResizeImage.resizeIfNeeded` + `gaplessPlayback: true` + 保持 `ImageStream` 存活（`_keepImageAlive`）。

**建议方向**：`Image.file()` 的缓存键问题、Navigator 过渡动画与图片解码的时序同步；可用 DevTools 时间线定位。

**验收**：录屏逐帧确认页面切换后背景图在首帧或第 2 帧内出现。

| 编号 | 约束 | 说明 |
|---|---|---|
| L-01 | 台账条目**只增不删**，修复后改状态而非移除 | 保留历史，便于回归对照 |
| L-02 | 每条必须有可核对证据（`文件:行`），否则不入表 | 防止「感觉有问题」 |
| L-03 | 严重级判定需有依据；P0/P1 升级必须说明影响面 | 避免优先级通胀 |
| L-04 | 台账与实际代码可能短暂不一致（修复中） | 以「状态」列为准，发布前复查 |
| L-05 | 部分条目为「待核实」，不能当作已确认缺陷 | 需先验证再排期 |
| L-06 | 与 `07-推进计划/任务分解-WBS.md` 的任务编号必须双向可追溯 | 防止问题无人认领 |

## 6. 维护纪律

| 规则 | 说明 |
|---|---|
| M-01 | 发现即登记：任何 PR 的评审意见若确认为问题，必须在本表新增条目 |
| M-02 | 编号不复用：修复后状态改为「已修复（版本号）」，**条目保留** |
| M-03 | 每条必须有「证据」（`文件:行`）与「验收方式」 |
| M-04 | 严重级变更必须记录原因（升/降级理由） |
| M-05 | 每次发布前复查 P1/P2 条目，在发布说明中列出未修复项 |
| M-06 | 每季度对全表做一次有效性核查（是否仍存在、是否已过期） |
